# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**This file is published.** It ships in the public repo and in every release tag, so write it as public copy. Internal hostnames, private instances, IPs, tokens, and anything else that only makes sense on a private server belong in `private_docs/` (gitignored) or in the global `~/.claude/CLAUDE.md` — never here. Removing such a thing later does not unpublish it: an internal host sat in this file from 2026-03-25 to 2026-08-14 and remains in the git history and in every tag cut during that window.

**Enable the pre-commit hook on every clone** — `core.hooksPath` is local config and does not travel with the repo:

```bash
git config core.hooksPath .githooks
```

It runs `scripts/check-no-leaks.sh` over the *added lines* of staged changes, blocking credentials, hardcoded home directories, public IPs, known-private hostnames, and files that should never be tracked. `scripts/check-no-leaks.sh --all` audits every tracked file. Bypass with `git commit --no-verify` — and if you had to, widen the exclusion in the script so the next person isn't trained to ignore it.

## What This Is

Vega is a cross-platform Nostr desktop client built with Tauri 2.0 (Rust) + React + TypeScript. It connects to Nostr relays via NDK (Nostr Dev Kit) and aims for Telegram Desktop-quality UX. Long-form content (NIP-23) is a first-class, distinguishing feature — not an afterthought.

## Commands

```bash
npm run tauri dev       # Run full app with hot reload (recommended for development)
npm run dev             # Vite-only dev server (no Tauri window)
npm run build           # TypeScript compile + Vite build
npm run tauri build     # Production binary
```

Prerequisites: Node.js 22.22+ or 24.15+ (24 LTS recommended), Rust stable, `@tauri-apps/cli`.

The floor comes from the test stack, not the build: vitest 5 needs Node 22.12+, and jsdom's dependencies now declare `^22.22.2 || ^24.15.0 || >=26.0.0`. `vite build` alone still accepts `^20.19.0`, which is why the Flatpak manifest's `node20` SDK extension still builds — but Node 20 reached end of life in April 2026, so move that manifest to `node24` when you next touch it. The old "Node.js 20+" line was stale from the vitest 5 bump (#88) until #99 made a reviewer notice.

## Releasing a New Version

**Order matters — do not tag before bumping versions.**

0. **Verify we are not shipping someone else's payload** — run the AUR check for **both** packages. Each must print `AUR package is clean.` (exit 0) before you tag:
   ```bash
   scripts/verify-aur-package.sh                                              # vega-nostr-git
   AUR_PKG=vega-nostr scripts/verify-aur-package.sh ~/projects/vega-nostr-aur # vega-nostr
   ```
   See "Distribution channel integrity" below for why this is step zero and not an afterthought.
1. Bump version to `X.Y.Z` in all **five** files (they must stay in sync):
   - `src-tauri/tauri.conf.json` → `"version": "X.Y.Z"`
   - `package.json` → `"version": "X.Y.Z"`
   - `package-lock.json` → run `npm install --package-lock-only` after bumping `package.json`
   - `src-tauri/Cargo.toml` → `version = "X.Y.Z"` (then `cargo check` to sync `Cargo.lock`)
   - `PKGBUILD` → `pkgver=X.Y.Z`
2. **Leave `.github/workflows/release.yml` alone.** Do not add per-version notes to `releaseBody` — see the release-notes rule below. Write the notes to a file and apply them after CI with `gh release edit vX.Y.Z --notes-file f.md`.
3. Commit: `git commit -m "Bump to vX.Y.Z — <summary>"`
4. Tag: `git tag vX.Y.Z`
5. Push: `git push origin main vX.Y.Z`
6. Update AUR — **two packages now**. In each checkout, bump `pkgver=X.Y.Z` in `PKGBUILD`, then:
   ```bash
   makepkg --printsrcinfo > .SRCINFO
   git add PKGBUILD .SRCINFO && git commit -m "Bump to vX.Y.Z" && git push
   ```
   - `~/projects/vega-nostr-aur` → **`vega-nostr`**. **This one is urgent and load-bearing.** It builds `#tag=v$pkgver`, so until `pkgver` is bumped and pushed, Arch users are still installing the *previous* release. This is the package the README points at.
   - `~/projects/vega-aur` → **`vega-nostr-git`**. Not urgent, safe to do late: it is a VCS package that builds the default branch, so its users already have the new code from the pushed tag whether or not `pkgver` moved. The bump is display metadata.

   Keep the two `build()` blocks identical — same `npm ci --ignore-scripts`, same `-- --locked`. Only the `source` ref differs. AUR git writes are gated independently of the website: the site can be HTTP 200 while pushes report "The AUR is down due to maintenance".
7. Re-run both AUR checks from step 0 after the pushes, so they also cover what you just published.

**`package-lock.json` is a version file.** CI runs `npm ci`, which *fails* on a package.json/lockfile mismatch — `npm install` used to reconcile it silently. Forgetting it breaks the build on all three platforms.

**The point of no return is `git push --tags`, not the release notes.** CI builds and publishes the binaries the moment the tag lands, so any behaviour change decided after that is not in the release, however early the notes still feel. Once a version's artifacts and its `latest.json` entry are public, **supersede with a patch release — never move the tag**: users who already updated would be running different code under the same version number, which is unrecoverable. Cost of superseding is one CI run. This was learned the hard way between v0.15.0 and v0.15.1.

CI triggers on the tag and builds all three platforms (Ubuntu, Windows, macOS ARM). All jobs must complete for `latest.json` to be assembled. The winget submission is a **separate** workflow (`winget.yml`) so a package-submission failure can't mark a good release red.

## Distribution channel integrity

Vega is shipped through channels that carry our name: the AUR, winget, GitHub releases, and Flathub. If one of them were adopted, modified or hijacked, we would be the ones distributing the payload. Being the vector is worse than being the victim, so this is checked on every release, not when something feels wrong.

- `scripts/verify-aur-package.sh` answers two questions: **is the AUR serving exactly what we pushed** (no tampering), and **did we actually push the current version** (no stale channel). Byte-identity covers the first on its own — an injected `install=` script, a repointed `source=`, or an added `prepare()` all have to appear in the PKGBUILD to take effect. Exit 0 clean, 1 mismatch, 2 couldn't check (treat 2 as unverified, not as a pass).
- **It compares against the AUR *remote*, not local `origin/master`, and reads content from the AUR *git repo*, not cgit.** Both matter, and both were wrong until 2026-08-14:
  - Comparing cgit against the local ref meant a missed push left *both sides equally stale* and the check reported clean. The v0.15.1 AUR bump sat committed-but-unpushed for a month behind a green tick, found only when v0.15.2 pushed two commits at once. A gate that passes while the channel is stale is not a gate.
  - cgit is a cached web view that lags the repo by minutes after a push — i.e. exactly when you run this — so it produced a false MISMATCH on the v0.15.2 release. AUR helpers clone the git repo, so the repo is what users get; cgit lag is now reported as an advisory note and never fails the check.
- The script also asserts the published `pkgver` matches `package.json`. Override with `AUR_EXPECT_VERSION` if you ever need to check a package you are not currently releasing.
- Prompted by the Arch advisory of 2026-06-12, "Active AUR malicious packages incident" — a high volume of malicious package *adoptions and updates*, with AUR submissions blocked in response. First run against `vega-nostr-git` on 2026-08-10: clean.
- A mismatch is never "probably fine". Investigate before announcing.

**Hard-won CI rules:**
- `uploadUpdaterJson: true` must be set in tauri-action — without it `latest.json` is never uploaded and the auto-updater silently does nothing. It was `includeUpdaterJson` before tauri-action v1.0.0; the old name is now an unknown input, which Actions accepts in silence, so writing it costs you the updater. See the v1 note below
- `bundle.createUpdaterArtifacts: true` must be set in `tauri.conf.json` — without it `.sig` files are never generated even if the signing key is set (Tauri 2 requirement)
- Valid `bundle.targets`: `"deb"`, `"rpm"`, `"nsis"`, `"msi"`, `"dmg"`, `"app"` — do NOT add `"updater"` (that's a plugin, not a bundle format)
- `"app"` MUST be in `bundle.targets` or the macOS auto-updater silently breaks: the `.app.tar.gz` updater artifact (and its `.sig`) is generated from the `app` target, NOT `dmg`. With only `dmg`, the `.app` is built as a throwaway intermediate, no `.app.tar.gz` is emitted, and `latest.json` gets no `darwin-aarch64` entry. `app`/`dmg` are macOS-only and skipped on Linux/Windows builds. This was broken from before v0.12.9 through v0.12.13; fixed in v0.12.14.
- macOS runner is `macos-latest` (ARM only) — `macos-12`/`macos-13` are gone
- Verify after CI: `https://api.github.com/repos/hoornet/vega/releases/latest` (check for `.sig` assets + `latest.json`)
- **Release notes in `release.yml` can trigger a GitHub workflow startup failure** ("workflow file issue", 0 jobs) that passes `yaml.safe_load` AND `actionlint`. Hit in v0.14.1 by 5 lines of plain-markdown release notes in the `releaseBody` block scalar; root cause never found. Keep the workflow's `releaseBody` minimal and known-good; put rich per-version notes on the release afterward with `gh release edit vX.Y.Z --notes-file f.md` — the release-body path doesn't go through the workflow parser.
- **`tauri-action` is on v1.0.0, pinned to its commit SHA**, taken at the start of the v0.15.8 cycle after holding through the v0.15.x line. Three things about that upgrade are worth keeping: `includeUpdaterJson` is **renamed to `uploadUpdaterJson`**, and because GitHub Actions does not error on unknown inputs, keeping the old name would leave `latest.json` unuploaded and the auto-updater silently dead — the precise failure the v0 rule existed to prevent. `uploadUpdaterJson` and `uploadUpdaterSignatures` both default to `true`, but ours stays explicit because it is load-bearing. And v1 renames the macOS updater artifact (`.app.tar.gz`/`.sig` now carry the version) while switching `latest.json` to github URLs rather than browser-download URLs.
- **Verifying a release means resolving a `latest.json` URL the way the updater does, not just seeing one.** Checking that the entries exist proves the generator ran; it does not prove the updater can download through them, and v1 changed exactly that field: since v0.15.8 every URL is an `api.github.com/repos/.../releases/assets/<id>` endpoint. **A plain `curl -sIL` on one returns `application/json` — that is expected, not a failure.** The endpoint serves the binary only to `Accept: application/octet-stream`, and the updater's download request sets exactly that header unless the app passes its own `Accept` (verified in tauri-plugin-updater 2.10.1, the version v0.15.7 users updated from; Vega's `check()` passes only `{ proxy }`). So test with `curl -sIL -H "Accept: application/octet-stream" <url>` and expect a redirect ending in `application/octet-stream` at the binary's size. It is broken if *that* returns JSON, or if Vega ever starts passing a custom `Accept` to `check()`. Do this before announcing, alongside the per-platform `.sig` and `darwin-aarch64` checks — and compare each `latest.json` signature against its `.sig` asset. v0.15.8, the first release through v1, passed all of it.
- **Tauri's Rust crates and npm packages must agree on major.minor, and only `release.yml` would notice if they don't.** `tauri build` refuses to run across a mismatch, but `test.yml` never invokes the Tauri CLI, so Dependabot's separate cargo and npm "tauri group" PRs merged green on 2026-09-27 with `tauri-plugin-http` 2.7.0 against `@tauri-apps/plugin-http` 2.6.1 — which would have failed v0.15.8 on every platform and broke `vega-nostr-git` (it builds main) immediately. `scripts/check-tauri-versions.mjs` now runs first in `test.yml` and compares the two lockfiles. Watch for the indirect case too: a plugin bump can drag `@tauri-apps/api` up a minor through its own dependency (plugin-http 2.7.0 needs api ^2.12.0), which then has to match the `tauri` crate. Don't swap the check for `tauri info` — it prints the mismatch error and exits 0.
- **Never write `@dependabot <command>` as literal text in a GitHub comment.** Dependabot parses commands out of comment bodies with no regard for surrounding prose — a sentence explaining why you would *not* run a command still runs it. Writing "`@dependabot ignore this major version` would be wrong here" in a comment on the tauri-action PR closed it and set a permanent 1.x ignore two seconds later; recovered with `@dependabot unignore tauri-apps/tauri-action`. Refer to commands descriptively ("the ignore-this-major-version command") instead.

## Supply chain

- The release job builds and signs what users install, so `release.yml` runs **`npm ci --ignore-scripts`, never `npm install`** — `install` re-resolves inside caret ranges, so a compromised patch release could reach a signed build without appearing in the reviewed lockfile.
- **`plugins.http.scopeRedirects` is on in `tauri.conf.json`** (tauri-plugin-http 2.7+). Without it the plugin checks the URL scope only against the URL the frontend asked for and then follows redirects anywhere: an allowed host answering `302 http://127.0.0.1:…`, an internal name or a cloud metadata address gets that response handed to the webview. With it, every hop must pass the scope, and a hop that doesn't fails with `url not allowed on the configured scope`. Our scope is `https://**`, so in practice this refuses redirects off HTTPS; LNURL, Fountain, Podcast Index, Vertex and the upload hosts all stay on HTTPS. Upstream makes this the default in plugin-http v3, so a request that starts failing on a redirect is a request worth looking at, not a reason to turn the option off.
- **All actions are pinned to commit SHAs**, with the version in a trailing comment. Tags are mutable; `tauri-action` runs with the signing key in env. Dependabot (`.github/dependabot.yml`, covering npm + cargo + github-actions) keeps the SHAs current.
- `@nostr-dev-kit/ndk` is pinned **exactly**, not with a caret. Upstream is effectively single-maintainer, last published 2026-02-23, and a request to enable private security reporting has gone unanswered since June (nostr-dev-kit/ndk#393). NDK moves when we choose to move it. Vega carries a NIP-46 workaround for it in `src/lib/nostr/nip46.ts`.
- Known-and-accepted `cargo audit` noise: 4 quick-xml DoS advisories (build-time via `plist`, and XML *writing* via `tauri-winrt-notification` — neither parses untrusted input) plus ~22 `unmaintained` warnings, mostly gtk3-rs, which is Tauri's Linux stack. The point of writing the baseline down is that **anything outside it is new**: that is how `h2` 0.4.13 surfaced (RUSTSEC-2026-0258, unbounded empty DATA frames — it affects the *client* side too, so a hostile relay endpoint, image host or update mirror could exhaust memory), bumped to 0.4.19.
- **Read the lockfile *diff*, not the version number, on every dependency PR — look for crate names that were not there before.** On 2026-08-20 three widely-used crates were hijacked on crates.io for 86–107 minutes each (`arrayref` 0.3.10, `internment` 0.8.7, `append-only-vec` 0.1.9). The payload was not in the crate's own code: each added a **new dependency** on `proc-macro1`, a `proc-macro2` typosquat, whose *build script* reassembled a base64 stage-2 credential stealer with TLS validation disabled. Compiling was enough. A committed `Cargo.lock` means such a crate cannot reach a signed build without appearing in a diff first — which is worth nothing unless someone reads that diff for new names, the one signal separating a hijack from an ordinary bump. Note the attacker also yanked the legitimate 0.3.5–0.3.9 so the trojaned release was the only non-yanked option: **being the newest unyanked version is not evidence of anything.** Vega's tree contained none of the three, and no typosquat has ever entered it.
- **Cargo runs with `--locked` wherever it gates a build.** This is cargo's `npm ci`: without it a `Cargo.toml` bump that never had `cargo check` run against it re-resolves silently and builds a lockfile nobody reviewed, instead of failing in seconds. `test.yml` has it. `release.yml` does not yet — add it through tauri-action's `args: -- --locked` (the Tauri CLI forwards trailing args to cargo) at the **start** of a release cycle, next to the tauri-action v1 decision, never mid-cycle.
- **`cargo audit` runs weekly on a schedule and opens an issue — it is not a pull-request gate.** As a required check it would go red whenever anyone publishes an advisory against a transitive crate we do not control, blocking an unrelated PR at an arbitrary hour, which trains everyone to wave it through. Accepted advisories live in `src-tauri/.cargo/audit.toml`, each with a written reason; an entry without one is an entry nobody will dare remove. Verify after editing that list that the audit still *fails* with an ignore taken out — a permanently-green gate is worth nothing.
- **`cargo update -p <crate>` re-resolves the whole graph, not just that crate.** Edges whose requirement spans several semver-incompatible versions get re-picked freely — `tempfile` and friends declare `windows-sys = ">=0.52, <0.62"`, and five `windows-sys` majors are already in the tree, so a three-crate security bump churned ~10 crates onto different Windows bindings that the Linux dev machine never compiles. Keep a security bump to the crates you meant to move, then prove the result with `cargo check --locked`, which fails unless the lockfile is a valid complete resolution.

## Events are checked before anything sees them

A Nostr client trusts nothing a relay says: an event counts because its author signed it. NDK 3.0.3 does not hold to that by itself, in two ways. Both let a relay hand Vega an event under anyone's name: a note, a profile, or the account's own follow list, which the next Follow click then republished under the user's own key. Both are shown with real NDK in `src/lib/nostr/authentic.test.ts`, each attack once against NDK as it comes (where it gets through) and once as the app builds it.

- **NDK samples signatures.** A relay's events stop being checked once the relay has "proved itself" (`shouldValidateEvent`, `validationRatioFn`). For a relay created after the NDK instance (one added in the Relays view, one from a published relay list, one reached through Relay reach, the built-in relay) a slip in NDK makes that total: the constructor builds the pool before it sets `validationRatioFn`, so only relays of the configured list get the safe default, and the rest get a method bound to the wrong object that works out the share to check as `NaN`. After ten good events and the next thirty-second tick, nothing such a relay sends is checked.
- **NDK's record of checked signatures is kept by the id an event claims**, and nothing compares that id with the hash of the event. A relay sends one honestly signed event under an id of its choosing, then a forged event under the same id within a minute: the record says "checked". This works from any relay, the configured ones included, and with every signature checked.
- **The fix is two rules in `src/lib/nostr/authentic.ts`.** Every relay's events are always checked (`NDKRelay.prototype.shouldValidateEvent` returns true). And an event whose id is not the hash of its own author, time, kind, tags and content is dropped before NDK looks at it (`guardIncomingEvents`, in front of `subManager.dispatchEvent`, the one place NDK matches an event from a relay to the subscriptions that want it, its own fetches included). The second rule is what makes NDK's "once per id" record sound.
- **Every `new NDK(...)` goes through `guardIncomingEvents`.** Five do: the main instance and the one that replaces it on a reset, the two wallet connections, the search relays. A test reads the sources for a `new NDK(` without the wrap in front of it; it is a lint, so keep new sites in that shape.
- **Verification must stay synchronous.** With NDK's worker (`signatureVerificationWorker`, `asyncSigVerification`) an event is handed to its subscription before the signature is known, and a bad one only raises `event:invalid-sig` afterwards; the id check does not cover a correct id over a forged signature. `guardIncomingEvents` refuses such an instance. If feed load ever needs verification off the main thread, that event has to be handled first.
- **Setting `validationRatioFn: () => 1` is not enough**, and setting `initialValidationRatio` and `lowestValidationRatio` to 1 does nothing at all for the first problem (still `NaN`). Neither touches the second.
- **Cost.** The id check is a hash, about five microseconds an event. Signatures were already checked for the relays of the configured list, which is where almost all events come from.
- **Private messages were not affected.** A gift wrap's sender is held to by NIP-44's authenticated encryption, not by the seal's signature alone.
- **Still open.** NDK also records a *failed* check by id for a minute. A relay that sends a real event with a broken signature first can make NDK drop the genuine copies from other relays for that minute: suppression, not forgery. Closing it needs NDK's own verification replaced, which is one more reason to fork or vendor NDK.
- **When NDK is upgraded, run `authentic.test.ts` first.** Its "by NDK as it comes" cases say what NDK does alone. If one of them starts failing, NDK changed, and the rule it stood for may no longer be needed, or may no longer be reached.

## CommonJS default imports (bundler gotcha)

`react-qr-code` (and any CommonJS-only lib) can crash a view: under Vite 8 / Rolldown, `import X from "cjs-lib"` may resolve to the module namespace object `{ ..., default }` instead of the component, so `<X/>` throws React #130 ("element type is invalid… got: object") and the error boundary blanks the app. This only shows in built bundles, not `npm run tauri dev`. `AboutView.tsx` keeps a defensive unwrap (`(X as ...).default ?? X`) — don't revert it to a plain default import, and use the same guard for other CJS libs rendered as JSX.

- Functional React components only — no class components
- Never use `any` — define types in `src/types/`
- Tailwind classes only — no inline styles, except unavoidable WebkitUserSelect
- Private keys stored in OS keychain via Rust `keyring` crate; nsec persists across restarts

## Relay reach & NDK's outbox model

The relay list is a promise to the user: if they delete every public relay, Vega must not phone home to anyone else's. Two NDK behaviours break that promise, and neither is obvious from the option names.

- **NDK enables the outbox model unless you pass a literal `enableOutboxModel: false`.** The check is `if (!(opts.enableOutboxModel === false))` — omitting the option, or omitting `outboxRelayUrls`, leaves outbox fully **on**. `core.ts` claimed for years that omitting `outboxRelayUrls` disabled it; it never did. With outbox on, a follow feed resolves every author to their NIP-65 write relays and connects to all of them — **29 relays observed against a configured list of one** (issue #35). This is also the mechanism CLAUDE.md blamed for the "pool balloons 7 → 40+, firehose into `startLiveFeed()` → OOM" crashes, which means that fix was never in effect either. `nwc.ts` always got this right; copy that instance's options, not the old feed ones.
- **Removing a relay from `pool.relays` does not stop NDK using it.** `calculateRelaySetsFromFilter` falls back to `ndk.explicitRelayUrls` for any filter it can't scope to authors and re-adds those URLs to the pool, so a deleted relay returns on the next subscription and only stays gone after a restart. `addRelay`/`removeRelay` must keep `explicitRelayUrls` in sync.
- **Never assign `ndk.explicitRelayUrls = [...]`.** The setter also runs `pool.relayUrls = urls`, which clears the pool and reconstructs every `NDKRelay` — silently dropping the embedded strfry relay, which lives in the pool but deliberately never in the stored list. Mutate the array in place, as NDK's own `addExplicitRelay` does.
- `relayConnectionFilter` is the enforcement point: NDK consults it in `NDKPool.addRelay` **and** in the OutboxTracker, where it prunes each author's discovered read/write relays. It does *not* gate `NDKRelaySet.fromRelayUrls`, which connects its relay objects directly — that's why NIP-46 bunker login still works, and why `fetchUserNotesNIP65` and the NIP-17 DM relay routing in `dms.ts` (#49) each need their own explicit `isOutboxRelaysEnabled()` gate.
- **`autoConnectUserRelays` is a *third* way relays enter the pool, and it also defaults to on.** On login, `setActiveUser` → `getUserRelayList` reads the signed-in user's **published** kind-10002 list and adds every relay in it with a plain `pool.addRelay()` — **no prune timer, so they stay for the life of the instance**. This is separate from the outbox model and from `explicitRelayUrls`, and it is why the pool settles *above* the configured count: measured 2026-08-15, two relays outlived the 30s prune while others were removed normally, and only the call-path stack showed why. It is gated by `relayConnectionFilter`, so Relay reach off does block it; it is now tied to the same switch explicitly rather than relying on the filter to catch it. Vega never set it before v0.15.3.
- **The temporary-relay pruner compares URLs with an exact string match**: `if (this.ndk.explicitRelayUrls?.includes(relay.url)) return;`. `relay.url` always carries a trailing slash (`NDKRelay` normalizes), but NDK's **constructor assigns `opts.explicitRelayUrls` verbatim** — only the setter normalizes. Passing the stripped form made every startup-configured relay read as disposable while runtime-added ones survived. Hand NDK `tryNormalizeRelayUrl` output; keep storage stripped. Note tests that strip slashes on both sides before comparing cannot see this class of bug — `relayConfig.test.ts`'s `hasUrl()` did exactly that.
- **`relayGoalPerAuthor` defaults to 2**, meaning each author in an `authors` filter is resolved to two of their NIP-65 write relays and connected to both — ~18–21 relays for one follow list. Capped at 1 in `fetchWithTimeout`; measured cold start went from pool 12 / 17 mutation events to pool 7 / 5.
- **The relay badge counts the pool, which is not the relay list.** It read "6/6 relays" for a configured list of three, because the pool also holds the embedded relay and everything NIP-65 pulled in. It now counts configured relays only, with a separate `+N` for extra reach — the absence of the `+N` is the signal that Relay reach is holding. Don't collapse those numbers back together.
- **`ndk.connect()` resolves only once every relay in the list has connected.** With one relay down it never does. `resetNDK` (behind the Relay reach switch and "Try again") awaited it unbounded until 2026-10-12, so the switch stayed busy for the rest of the session once #130 gave it a busy state. Every wait on `connect()` takes a time limit; what matters is `waitForConnectedRelay`, one relay up or the limit. `resetNDK.test.ts` holds it, against addresses that never resolve.
- Verify this one **in the running app, on the Following tab.** Global sends no `authors` filter, so it exercises none of the outbox machinery and looks fixed no matter what. The first attempt at #35 passed its unit tests and was still completely wrong on Following.
- **Count the configured list before calling a pool size wrong.** #36 reported the pool settling at "4 vs 7 expected" as a possible bug; the stored list actually held three relays, not six, so 3 + the embedded relay = 4 was correct all along. Read `getStoredRelayUrls()` at the time of measurement rather than trusting a remembered number.

**Why outbox stayed on by default**, despite being what #35 reported: it had been silently enabled for the app's entire history, so every release users were happy with shipped *with* it. Switching it off would have been the untested change, not the conservative one — and the OOM crashes it was blamed for turned out to be the Blossom regex, fixed in v0.12.8, since outbox was never actually off during any of that. Users who want Vega confined to their own list opt out; everyone else keeps the reach they already had. The toggle lives in the Relays view, because someone who wants it is already on that screen; Settings points there.

## NIP-42 relay AUTH

AUTH signs a kind 22242 with your identity key, so every relay you answer learns who you are and can link that to everything you ask for afterwards. That makes it a privacy setting, not just a protocol feature — hence the **Relay authentication** switch (*Only my relays* by default / *Any relay that asks*), in the Relays view (it was also in Settings until October 2026). Added in v0.15.5 for issue #48; before that Vega had no NIP-42 code at all, so an auth-required relay simply never delivered kind 1059 gift wraps, for nsec and bunker logins alike.

- **The policy returns `true`/`false`, never a signed event.** On `true`, NDK builds and signs the 22242 itself with `ndk.signer` read at signing time, sets the relay to `AUTHENTICATED`, and retries publishes that were blocked awaiting auth. The `NDKEvent` return path does none of those. Do not reach for `NDKRelayAuthPolicies.signIn` either: it caches `signer ??= ndk?.signer` into a closure it never clears, so after an account switch it authenticates as the **previous identity**.
- **`authed` fires twice, and the first one is a lie.** `onAuthRequested` calls `authenticate()` fire-and-forget, then runs `_status = CONNECTED` and `emit("authed")` synchronously — before the event is signed. Measured against `nak serve --auth`: `[5, 5, 8, 8]`. The only reliable test is `relay.status === NDKRelayStatus.AUTHENTICATED`. The gap is sub-millisecond with a local nsec and seconds wide with a bunker, so keying on the event works on the dev machine and fails for the person who reported the bug.
- **Never assign to `relay.authPolicy`, only `ndk.relayAuthDefaultPolicy`.** NIP-46's RPC pool sets its own per-relay policy using the ephemeral client key; overwriting it would authenticate to bunker relays as your main identity.
- **"My relays only" includes the user's own published kind 10050 DM relays** (#49). A dedicated DM inbox relay is exactly the relay that gates kind 1059 behind NIP-42 and exactly the relay a privacy-minded user keeps out of the configured list — without this the DM relay routing reaches the relay only to refuse its challenge. The registry lives in `relayAuth.ts` (leaf, so core.ts can read it without a cycle), is populated when dms.ts resolves the user's own 10050, and MUST be cleared on identity change (`dropAuthenticatedSessions` does). A *recipient's* DM relays get no scope widening — we publish to them without identifying ourselves.
- **The policy must be one stable module-level function that reads the scope per challenge.** Reassigning `ndk.relayAuthDefaultPolicy` later does not reach relays built by `getUserRelayList` or `NDKRelaySet.fromRelayUrls` — those capture the value into `relay.authPolicy` at construction, and that wins the `??`. Reading the setting at call time is also what makes the switch live without a reconnect.
- **Declining leaves the relay stuck at `AUTHENTICATING`** for the life of the connection — the re-entrancy guard in `onAuthRequested` then ignores every later challenge. It clears on reconnect, so the only way to act on a scope change (or on logging in after declining for lack of a signer) is `rechallengeRelays`, which bounces the connection.
- **Changing identity must drop authenticated sessions.** `switchAccount` clearing `ndk.signer` is not enough: AUTH binds identity to the *connection*, so a relay authenticated as account A keeps serving account B under A. On a relay with `restrictReadToInvolvedPubkey` that shows up as B's inbox being empty — the same symptom as #48, caused by the fix.
- **Becoming someone else means letting go of the last account first: its key, and its sessions.** Until October 2026 only `switchAccount` and `logout` did. A read-only sign-in (`loginWithPubkey`, "Add account" with a public key) left the last account's key in `ndk.signer`: the screen said B, read-only, and whatever asks only "is there a signer" (the podcast list, the mute and bookmark lists) published as A, in place of A's own lists. Signing in with another key or bunker replaced the key and kept A's sessions, and so did removing the active account. All of those let go now, and so do the two branches that end signed out after a wait (a switch whose key or signer did not turn up, a bunker restore that failed). `useCanSign` reads the login type, `getNDK().signer` the key in hand: when they disagree, the key wins, so a function that signs for an account should check that the key is that account's (`publishPodcastList` does).
- Still open there: two switches that overlap. `switchAccount` and `restoreSession` wait up to half a minute for a signer, and the one that finishes last decides the key, whichever was asked for last. A sign-in that throws after its key was put in place leaves that key behind.
- **Never call a bare `sub.stop()`.** Use `stopSubscription()`. See the orphan-subscription note below; arming AUTH is what makes that hazard live.
- Verify with `nak serve --auth` (challenge on rejection) **and** `--eager-auth` (challenge on connect) — the orderings differ, and a test that attaches its listener after `connect()` silently observes nothing in eager mode.

## Relay liveness

`relay.connected` answers "did this socket ever open", not "is anything reachable". A network taken away without a FIN or RST — a KVM switch, a suspended laptop, an interface handover — leaves the socket ESTABLISHED. NDK 3.0.3 does have a keepalive (checked 2026-10-11): a REQ probe after 120 s of silence, a 5 s `readyState` check and a sleep detector, and `handleStaleConnection` closes the socket before reconnecting. So a dead socket is closed within about two minutes, but the flag reads `true` until then, reads `true` again on the new socket while the network is still gone, and a close sent with the uplink down never reaches the server (which is why relay-side keepalive matters too). Issue #65: Messages stopped loading and only an app restart fixed it. An earlier version of this section said NDK has no heartbeat; the heartbeat exists, and the rules below hold because the flag lies between its probes.

- **Liveness comes from fetch outcomes, never from socket state.** An EOSE proves a relay answered; three consecutive fetches that time out having collected nothing mark the pool silent (`isPoolSilent()`). Everything that asks "are we connected?" consults that as well as the flag.
- **Never re-add an active probe.** `2e03c6c` had one: it force-disconnected relays whose 3s probe timed out, killing healthy-but-slow relays and death-spiralling against `resetNDK`. Nothing may disconnect a relay on suspicion. Reporting is safe; disconnecting is not.
- **The relay badge follows the connection monitor, not the sockets.** With the feed store's `connected` false it reads "N relays, not answering" in red, whatever `relay.connected` says, and its list says the dots are open sockets, not listeners. It read "5/6 relays" in green through a whole offline test on 2026-10-12.
- **The embedded relay must never answer the question.** It lives on `ws://127.0.0.1` and survives any network failure, so `some(r => r.connected)` was permanently true for anyone who enabled it — silently disarming `ensureConnected` *and* the feed store's monitor. Excluded from both, with a fallback so a pool holding only local relays still counts.
- **A verdict that cannot be revisited is a deadlock.** Every path that could clear the silent streak is gated behind `ensureConnected`, so returning a bare `false` made the DM view's "Try again" a button that could never succeed. It re-tests with one cheap fetch, which feeds the same signal and clears the streak when the pool is genuinely back.
- **The connection monitor's escalation was dead code from the start.** `if (offlineStreak >= 3 && get().connected)` set `connected` to `false` as its first statement, so every later tick skipped the block: the per-tick `connect()` retry and the 30s `resetNDK()` had never once fired. It went unnoticed because cleanly-closed sockets are reconnected by NDK itself — only a half-open socket needs the ladder, and that is exactly when it wasn't there.
- **Reproduce with `SIGSTOP`, not a firewall.** Freezing the relay process holds the connection ESTABLISHED while nothing is answered — a real half-open socket, no privileges. Start it **detached** (`setsid nohup`): a supervisor that reaps stopped children turns the freeze into a clean close, which silently tests the wrong thing. `connectionLiveness.live.test.ts` asserts `relay.connected === true` mid-test for exactly that reason, and caught it.
- Messages is where any relay outage surfaces first, because it is the only major view with no SQLite cache — everything else keeps rendering what it already had and looks healthy.

## Orphan relay subscriptions

`sub.stop()` on a subscription that is RUNNING and has never EOSEd hits an early `return` in NDK's `NDKRelaySubscription.removeItem`, which skips both the CLOSE frame and `cleanup()`. Skipping `cleanup()` strands the `relay.once("authed", reExecuteAfterAuth)` listener that `execute()` registers whenever `relay.status < AUTHENTICATED`. When `authed` later fires, that zero-item subscription re-executes with no filters, and `req()` builds its frame as ``["REQ","${subId}",${JSON.stringify(filters).substring(1)}`` — where `JSON.stringify([]).substring(1)` is `"]"`, putting `["REQ","<id>",]` on the wire. That is invalid JSON; relays treat a parse error as fatal, so the socket drops, NDK reconnects, the relay re-challenges, and each cycle costs another signature.

A relay answering `CLOSED auth-required:` never sends EOSE, so this is the shape every auth-blocked fetch leaves behind, and the 60s notification poller manufactures two per minute per auth-required relay. `pruneOrphanRelaySubscriptions` sweeps them, and the policy calls it before returning `true` — the last hook before the ghosts discharge, since tseep emits synchronously.

## Contact list (kind 3) and NDK's early EOSE

A kind 3 is replaceable: publishing one replaces the user's whole follow list, for every client they own. Until v0.15.9 `follow()` built that event from whatever was in memory, and "the list did not load" looked exactly like "the list is empty". One Follow click could turn 131 follows into one.

- **NDK ends a multi-relay fetch early, and `closeOnEose` then drops the rest.** `NDKSubscription.eoseReceived`: once two relays and half of the connected ones have sent EOSE it waits `1000ms x (1 - fraction)` for the others, so with four relays the slowest gets **250ms after the third**. Anything only it holds is lost without a trace. Measured 2026-10-11: a contact list held only by the slowest of four default relays failed to load in 15 of 15 attempts, each returning "nothing" in a steady ~427ms. This is the likely root cause of the whole "relays returned empty" class the retry-on-empty pattern was added for. `NDKUser.follows()`, `fetchEvent` and our own `fetchWithTimeout` all inherit it.
- **For a single replaceable event, ask each relay on its own.** `fetchFromRelay` (core.ts) subscribes with a relay set of one, where there is no quorum to cut short: EOSE means that relay is done, a timeout means it never said. `fetchContactList` (social.ts) fans it out and returns one of three results, and they must stay distinct: `found`, `none` (every remote relay finished and none has a list) and `unknown`. Never collapse `unknown` into an empty list.
- **Never publish a kind 3 that was not built from a loaded list.** `changeFollow` (user.ts) re-fetches, takes the newer of that and what this session already holds, applies one change with `nextContactTags`, and publishes the full tag set and content. Relay hints, petnames, non-`p` tags and the legacy relay JSON in `content` survive. If the relays could not tell and nothing is held, it publishes nothing and says so. `publishContactList` takes tags and content, deliberately not a bare array of pubkeys.
- **`follows.length === 0` means nothing without `followsStatus === "loaded"`.** Anything that reads an empty list as "follows nobody" must check the status; the Following tab shows loading, could-not-load (with Try again) and genuinely-empty as three states.
- **The list is cached per account in localStorage (`wrystr_contact_list_<pubkey>`).** It shows the list at once on startup, and it is why a relay that is slow, down, or has lost the event cannot shrink the list: the cache is the base, and the next change republishes it. A corrupt entry must parse to "no cache", never to an empty list.
- **The embedded relay cannot vouch for absence.** It answers instantly with the network gone, so its copy of a list counts and its silence proves nothing.
- **The mute list (kind 10000) and the bookmark list (10003) follow the same rules**, through `src/lib/lists.ts` and `fetchReplaceableList` / `publishReplaceableList` (`src/lib/nostr/lists.ts`; `fetchContactList` is the same reader with kind 3). Until October 2026 both stores published the list as this device held it, whole, over whatever the relays had, with `content` (where other clients keep their private items) written empty every time and every tag but `p`, or `e` and `a`, dropped. Now, per account, the store keeps the relays' list as last read (the base, `wrystr_mute_list_<pubkey>` / `wrystr_bookmark_list_<pubkey>`) and a record of *which* entries this device added or removed since (the changes, `wrystr_*_changes_<pubkey>`). What is shown is the base with the changes applied; what is published is the same, built from the newest list the relays hold at that moment (`reconcile`: read, apply, publish, as the podcast list does), and nothing is published while no relay has returned a list. A removal made here holds until it goes out, instead of being undone by the next load. The lists older builds kept for the whole computer become the account's changes the first time it is seen, so nothing a user muted or saved is lost and nothing is published over a longer list. **Two gaps remain, shared with the contact list and pinned in `lists.live.test.ts`:** a relay that is *down* may hold the only list, so every connected relay says "none" and this device's list goes out as the first; and a relay that is *silent* (connected, not answering) may hold a newer list than the one an answering relay returned, which this device has never seen and so builds on the older copy, and the newer list loses once the silent relay wakes. Neither can be closed from this side: what a silent relay holds cannot be asked while it is silent. A relay that is silent and holds the only list is safe: nothing is published.
- **Still open:** a first login on a device with no cache, where the only relay holding the list is unreachable (not merely slow) and every reachable relay answers "none", still starts a new list. The old one survives on that relay but would lose to the newer event.
- **Verify this class in the browser dev build against real relays**, with publishing blocked at the socket (wrap `WebSocket.prototype.send`, drop `["EVENT"` frames, record what was attempted). Restart the Vite server after editing a store: HMR gives the module a new URL, and `import("/src/stores/user.ts")` from the page then returns a second, empty copy.

## NIP-46 remote signers (bunkers)

- **Every path that produces a NIP-46 signer must call `acceptSecretEchoAsAck`, not just fresh login.** NIP-46 lets a signer answer `connect` with either `"ack"` **or the secret** from the `bunker://` URI; NDK accepts only the literal `"ack"` and rejects everything else with `response.error`, which is `undefined` on a successful echo — hence "login failed: undefined". Bunker46 does `result = connection.secret || 'ack'`, so it echoes. Crucially `toPayload()` **persists the secret** and NDK re-sends it with `connect` on *every* `blockUntilReady()`, so a restored session hits the same echo on every reconnect. Fixing only the login path (#17) left restart permanently broken (#47) while login looked fine.
- **A failed bunker reconnect must not rewrite the account's login type.** `switchAccount` hardcoded `wrystr_login_type = "nsec"` on its failure path, so one missed reconnect sent the *next* startup down the nsec branch — which has no bunker signer to restore. That turned a transient failure into a permanent read-only account recoverable only by adding a fresh `bunker://` URI.
- **Always race `blockUntilReady()` against a timeout.** An unreachable bunker leaves it pending forever — it neither resolves nor rejects — so restore and account-switch hung with no error. Use `connectWithTimeout`.
- **Reproducing bunker bugs needs a bunker that echoes the secret**, and neither `nak bunker` nor NDK's own `NDKNip46Backend` does — both return a hardcoded `"ack"`. `scripts/echo-bunker.mjs` imitates Bunker46 for exactly this. Run it against `nak serve`, then `VEGA_BUNKER_URI=… npx vitest run nip46.live`; `src/lib/nostr/nip46.live.test.ts` is gated on that env var so CI stays hermetic, and needs `// @vitest-environment node` (undici's WebSocket dies under jsdom).
- Verify this class of fix **in the running app**, not just in tests: the defect is in *when* the reconnect runs and how the store reacts, which unit tests can't see. Seed a scratch profile's localStorage (`wrystr_accounts` / `wrystr_pubkey` / `wrystr_login_type`) with a bunker account and launch against `XDG_DATA_HOME=<scratch>`.

## Layout rules (from the October 2026 UI review)

- **Lists and feeds share one content width: `.content-column` (42rem / 672px), in `src/index.css`.** The class goes on the *scroll container*, where it centres the content with padding, so the scrollbar stays at the edge of the pane. Use `.content-column-block` for a block outside a scroll container (the compose box). Before this every list ran the full width of the window: 140-character lines and, at 1920 wide, a single photo 1,636px across and taller than the window. A new list view gets the class; do not set a width per view.
- **Anything `position: fixed` that can be opened from a feed row must render through `BodyPortal`** (`src/components/shared/BodyPortal.tsx`). `Dialog` does, so a dialog needs nothing more. Feed rows are positioned with a CSS transform (the virtual list), and a transformed element is the containing block for fixed descendants: a dialog mounted in a row dimmed one note, was centred on it, and scrolled away with the feed. The portal wrapper carries the text-size zoom, which lives on `<main>`.
- **React events bubble out of a portal to its React ancestors.** A component that treats a click anywhere inside it as navigation (`NoteCard`) must check `e.currentTarget.contains(e.target)` first, or clicking a label inside a dialog opens the thread behind it.
- **The avatar row in a note is `items-start`.** Without it the avatar button stretches to the card's height and centres the picture: on a tall post the face sat hundreds of pixels below the name, and the whole strip opened the profile.
- **A lone feed image keeps its fixed 4:3 frame** (the virtual list needs the height before the picture loads) and is fitted by `soloImageFit` in `src/lib/mediaFit.ts`: fill the frame when the picture is about that shape, show it whole otherwise. The frame is capped at 70% of the window height.
- **The feed opens on the tab the user picked last** (`wrystr_feed_tab`), otherwise Following when signed in and Trending when not. Tabs the app picks as a default are passed `{ remember: false }` to `setFeedTab`, so only the user's own choice persists. An account that follows nobody is sent to Trending once, and only after the follow list actually loaded.

## Long-form reading

Articles are what Vega is for, and until October 2026 the reader was a markdown renderer in whatever serif the machine had, the list was one wide grey block per article with five tag chips that did nothing, and Articles opened on everyone's writing. The rules below came out of the October 2026 UI review.

- **The reading face is bundled: Literata, variable, weight axis and its italic** (`@fontsource-variable/literata`, imported in `main.tsx`). `--font-reading` names it first and Georgia after. 355 KB of woff2 over all its subsets; the optical-size axis is left out. The easy-read setting swaps the reading face for Atkinson too: articles are the one long-reading surface, and the setting used to skip them.
- **The reader's sizes are em on a fluid base, set in CSS** (`.reader-page`, `.reader`, `.prose-article` in `index.css`), not steps of the type scale. The body is `clamp(17px, …, 21px)` by window width (17 at 900 wide, 18 at 1200, 19.4 at 1600, 20.5 at 1920) on a 34em column, about 70 characters a line at every width, and never under 16 device pixels whatever the text-size preset (`--ui-zoom`, set in `App.tsx`). Title 2em, standfirst 1.2em, headings 1.5, 1.3, 1.12 and 1em at line height 1.25, with no rule under them. The type-scale ratchet cannot see CSS, and here that is the point: a `text-[2em]` class would be counted, and the reader is the one place a size may follow the window instead of the UI scale.
- **The fluid size sits on the page container and the column inherits it.** The grid that puts the contents list beside the text measures its middle track in the container's em. Set on the column alone, that track read 34em at the UI size and squeezed the text to 510px on a 1600 window; the measured text widths after the fix are 613, 659 and 697px at 1200, 1600 and 1920.
- **A first heading equal to the title is stripped from the body** (`stripLeadingTitle`, `src/lib/article.ts`), from the markdown and before it is rendered: writers often open with `# Title`, and the reader already shows the title. Not from the HTML afterwards: the rendered HTML is DOMPurify's and is not taken apart again (CodeQL read a tag-stripping regex on it as a sanitiser, which it was never meant to be).
- **The reader is keyed by the article's address in `App.tsx`**, so "More from" or Back opens a new instance: a comment or a like still on its way for the last article cannot land on this one, and nothing is reset by hand. The view stack keeps the open article, so Back from "More from" or from the writer's profile returns to the article that was open, not to the one just left.
- **The cover comes after the title, standfirst and byline, capped at 2:1 and 320px.** A 640×360 cover used to be the whole first screen at the minimum window size.
- **Read means read.** An article is marked read in the reading list when the reader is 90% of the way through the text, or when all of it fits the pane, not on open: a mis-click used to clear the unread dot and the sidebar badge. Progress is measured to the end of the body (`readingProgress`), not of the page: the footer, the writer's card and their other articles come after the text, and measured over the whole page the last paragraph of a short article sat at 60%. A picture that loads runs the check again, because it can make a short article fit or stop fitting. The reading list's "Mark read" is a visible button in the card's footer, not hover-only text.
- **Body images: a 16:9 box until the picture has loaded, then its own shape, never wider than it is** (`fitArticleImage`, applied on `load`, which does not bubble and is caught in the capture phase; it sets a maximum width and the picture's ratio, not a width, so the column may change afterwards). The 16:9 box is the WebKitGTK scroll-lock workaround (a decoded `<img>` sometimes collapses to 0 height, see the Linux lessons) and must stay for images that have not loaded. **Check body images in the real binary**, not only in the Chromium harness.
- **Code gets the theme's colours, not a bundled highlight stylesheet.** `atom-one-dark` was 1.6 to 2.3:1 on the Reader theme. Eight `.hljs-*` rules in `index.css` map tokens to `accent`, `success`, `zap` and `text-muted`. A code block sets its own line height (1.55) and size (0.82em); tables have borders; h4 to h6 have sizes.
- **The end of an article is the writer**: an author card (avatar, name, two lines of bio, Zap, Follow) and "More from {name}", up to three of their other articles (`fetchAuthorArticles` through `useLoadedList`, asked a second time after an empty answer; nothing is shown when there are none or no relay answered). **A writer's articles are asked of each relay on its own** (`fetchFromRelay`, as the lists are), plus the writer's write relays with Relay reach on. One fetch over the pool inherits NDK's early EOSE: measured 2026-10-17, two relays said "nothing" within 80 ms, the wait for the third was cut to about 330 ms, and the one relay holding the writer's articles answered at 368 ms, so the fetch returned nothing every time. The profile's Articles tab uses the same function and gains the same. The comment box opens under the footer row, where the button is; it used to open at the top and scroll the reader back to the title.
- **Header actions are icon-only `Button square`s**, 32×32, each with `aria-label` and `title`: Save, Zap, Repost, Comment, Copy link. Five labelled buttons did not fit at 900 wide. `square` is for a button that is only an icon and demands a name. Copy link copies an `njump.me` web link, which opens anywhere; the `nostr:` address is for other clients only.
- **Reposted is kept in `stores/reposted.ts`, per account and article**, as in the feed, so it survives reopening. Liked is still local state.
- **The card (`ArticleCard`)**: byline (20px avatar, name, date; `showAuthor={false}` on the writer's own profile), the title in the reading face at `text-heading`, clamped at two lines (the clamp is on a block inside the title's button: on the heading it did not count the lines of an inline-block button), two lines of summary (the writer's, else the first 160 characters of the body, either way without a leading repeat of the title: `cardSummary`), a footer with the reading time, at most two tags as plain text and Save for an account that can sign, and a 144×96 cover beside the text whose column goes when it fails to load. The reading list passes `read` (a dot before an unread title) and `actions`. The footer has a fixed minimum height, so a row is the same height signed in or out.
- **The body is read for the card's summary, so it is read with limits** (`plainWords`): the first 4,000 characters, and every pattern bounded to a line or a length. A relay can hold any kind 30023, and this runs for every card in a list; with `^\s*` and unbounded brackets it took 12 seconds on 100 KB of newlines. `article.test.ts` holds hostile inputs under 50 ms.
- **The Trending feed estimates the card's height** (`feedEstimate.articleHeight`), so a change to the card's layout means measuring again, not adjusting by eye. Measured 2026-10-17 against 38 rendered cards: 1.5% mean error, 36 within 15%; the two outside were a long-word title that wrapped early and a cover that failed to load, which the estimate cannot know.
- **Articles opens on Following** for a signed-in account and on Latest when signed out, and remembers the user's own pick (`wrystr_articles_tab`; `setArticlesTab` with `remember: false` for the app's defaults, as the feed does). Signed out is decided in render and never written to the store: while a session is still being restored the user is not signed in yet either, and a write then kept them on Latest for the session. An account whose follow list has loaded empty is sent to Latest once; one whose list is loading or could not be loaded stays. The tab is in the ui store, so Back from an article lands on the tab it left. Scroll position is not kept yet.
- **The contents list sits beside the text** on a pane 1180 or wider (a container query on the reader's page, not a window breakpoint: the sidebar takes up to 360px of the window), in the third column of the reader's grid, two lines per entry, the active entry in full text colour with a 2px accent border. It used to be pinned to the far edge of the window.
- **Known gaps.** Liked does not survive reopening. Scroll position is lost on Back. The reading list is still a tab of Bookmarks. A wide table scrolls sideways within the column. The update banner's changelog has a compact stylesheet of its own (`.prose-compact`).

## Long-form writing

The editor (`ArticleEditor.tsx`), rebuilt after the October 2026 UI review. It was a form: 14px monospace across the full window, a toolbar strip between the title and the body, summary and cover behind a button called "Meta", and a Publish that fired on one click. On success the draft was deleted, which swapped the editor for the drafts list, so "Published" was never seen and two seconds later `goBack` dropped the writer on an unrelated view. And every publish minted a new address, so a typo meant a duplicate article.

- **Writing happens on the reader's surface.** The editor sits in `.reader-page` / `.reader` (the fluid measure above), the title is a `.reader-title` input, the body a textarea in the reading face at the reader's size (`.reader-field`, in the components layer so `font-mono` can still override it) that grows with its text. "Mono" switches the body to a monospace face (`wrystr_editor_mono`). The toolbar is above the title, inside the column. Zen is the same surface with the chrome hidden and the window full screen, so paste and drop still upload.
- **Preview is the reader.** `ArticleBody` (title, standfirst, byline, cover, body, the image fit and the lightbox) is one component used by `ArticleView` and by Preview, so what a writer sees is what a reader will. Preview used to have a stylesheet of its own at another size with no cover or byline.
- **Publish opens a sheet** (`PublishSheet`, a `Dialog` of the new `lg` size): the card as it will look in Articles (`ArticleCard` with `preview`, which opens nothing and offers no Save), over Summary, Cover and Tags, and one button. The summary is started from the first 160 characters of the body when the writer gave none, because the summary is what the card shows. "Details" opens the same sheet to fill those in without publishing. On success the article is opened (`openArticle` with the published event) and only then is the draft deleted; a failure stays in the sheet with the draft kept, and the fields are read-only while the article is on its way. `previewArticleEvent` (`lib/nostr/articles.ts`) builds the unsigned event the card shows; a cover is handed to it only once it looks like an address, so typing one does not request "h", "ht", "htt". The summary the body gives (`cardSummary`) is the field's placeholder and is used at publish when the field is empty, so no article goes out without one; it is not written into the field, where an early draft's first lines would have frozen.
- **An edit keeps its address.** "Edit" in the reader's header (your own articles) makes a draft from the event with its `d` tag and first `published_at` (`createDraft(fields)`, `ArticleDraft.dTag` / `publishedAt`); `publishArticle` reuses both (`articleTags`, pure and tested), so relays replace the article as NIP-23 intends. The header says "Editing a published article" and the button "Publish update".
- **A draft exists once something is typed.** With no drafts, Write Article opens on a blank page, not on "No drafts yet." with the action in the far corner; the draft is made at the first auto-save with anything in it (`isEmptyDraft`), and empty drafts are dropped when the editor is left (`pruneEmptyDrafts`), so the sidebar never counts a draft nobody wrote. The editor keeps the id of the draft it made (`draftId` ref), so the draft appearing in the store does not reload the fields under the writer's hands; when that draft is gone (pruned, deleted from the list) the id goes with it, else every save updated a draft that no longer existed while the status said "saved just now". **The fields are saved when the editor is left** (`save` in the unmount cleanup and before Drafts), so the last second of typing is not lost to a navigation; not after a publish, whose draft was deleted on purpose. "Drafts" is offered only when the list would have something in it.
- **The title and the body grow with their text, and the pane keeps its place.** Measuring a textarea means collapsing it first, which let the pane's scroll position fall: a writer at the end of a long article was thrown to the top on every keystroke. `grow` saves and restores the pane's `scrollTop`, and runs again when the column changes width or the reading face arrives (a `ResizeObserver`, `document.fonts.ready`). The title is a one-row textarea that wraps as the reader's title does; Enter in it moves to the body.
- **One edit draft per article**: Edit on an article that already has a draft with its `d` tag returns to that draft instead of making a twin whose stale publish would replace the newer one.
- **Deleting a draft can be undone**: a toast with Undo (`restoreDraft`) for six seconds, instead of an 11px × that deleted at once. Rows show an excerpt (`cardSummary` of the body), the reading time and how long ago.
- **The toolbar's rules are pure** (`src/lib/markdownEdit.ts`, tested): Bold and Italic with nothing selected put the marks down and the caret between them (they inserted the literal `**bold text**`), and leave a selection's edge spaces outside the marks; Heading, Quote and List go at the start of every line the selection touches (not a line the selection only reaches the start of) and come off again when every line has them (they went at the caret: `My heading## Heading`); a fence starts on its own line; Enter inside an item's text continues the list with the same marker or the next number, ends it on an empty item, and is a plain line break at column 0, inside the marker, or while an IME composition is being committed. `applyEdit` puts an edit on the textarea through `document.execCommand("insertText")`, which keeps the undo stack and fires `input` for the controlled value; where that is not available (tests) it sets the value. Replacing the whole value from state reset undo on every button.
- **Not done yet**: a real markdown editing surface (dimmed syntax, sized headings), a split view on wide windows, drafts in SQLite with export, Tab to indent a list item.

## Relays

Rebuilt after the October 2026 UI review, which judged that a normal person could not operate the view safely: nothing said what a relay was; the list mixed relays the user chose with relays Vega reached on its own, in identical rows, so a list of four showed eight; a relay that failed one probe was red, "offline" and one click from a danger-coloured "Remove dead", while the same row's purple dot said it was connected; per-row remove was hover-only, 35×16px, instant, with no undo; "Publish list" said nothing about what was published or to whom.

- **One sentence first**: "Relays are the servers Vega gets posts from and sends yours to. The defaults work; you can leave this alone."
- **Two lists.** "Your relays" is the stored list: the health results for relays still in it, plus every stored relay not checked yet, whether or not it has reached the pool (a configured relay must never vanish from its own list). Each row is removable. "Extra reach, found automatically" is what NDK pulled in on its own (`useRelayStatus`, which polls the pool so the count moves when Relay reach is flipped and NDK is rebuilt: origin "discovered"), collapsed to a count, not removable (it is not in the list), with the Relay reach switch directly under its heading. The built-in relay is in neither. Helper texts say "your relays", never "the relays listed above".
- **Nothing is removed without a word and a way back.** The per-row Remove is a visible 28px icon button named for its relay, and the toast it raises has Undo, which adds the relay back. **A fresh install sets the Vega-relay migration flag when it first reads the defaults** (`getStoredRelayUrls`): without it, the first list a new user ever saved, their first Remove, was read back as an existing user's list and the relay put back at once, under a toast that said "Removed". Nine test files were setting the flag by hand to keep that injection out of their lists. **`removeRelay` compares normalised addresses**: the pool's URL carries a trailing slash and the stored one does not, and a row drawn from the pool once removed the relay from the pool and left it in the list, back at the next check, under a toast that said "Removed". "Remove N relays not answering…" is offered only for relays that did not answer the last check **and** are not connected right now (one failed probe is weak evidence; a relay the pool holds a connection to is not dead), never for the whole list, and never while the network is down (every probe fails then, and the view says so instead). It opens an inline confirmation that names them, with Remove and Keep; Keep has focus, Escape keeps, and focus returns to the offer.
- **One status word, and nothing claimed without evidence**: "connected", "slow", "not answering" beside one coloured dot (the purple "NDK connected" dot is gone); a relay not checked yet says "not checked yet", an extra-reach relay "connected" or "not connected", and a relay whose probe failed while the pool holds a connection "connected, didn't answer the check". The header's "not answering" count is the relays that would be offered. The relay's name comes first and its address second. "Check now", and "Checked 4:25 PM". The health store keeps results only for relays still in the list, and a check asked for while one runs follows it.
- **"Share my relay list"** says what it does ("Tells other apps and people where to find your posts. Do this after changing the list."), the result is a toast, and after any add or remove, Undo included, "not shared yet" stands beside the button (on the canvas, not on the button's fill, where the warning colour is under 4.5:1 in the light themes) until a share goes out for the list as it was when the share began (`useRelayListShare`, a store, because Undo runs from a toast after the view may be gone). Per device, as the list is: a share by another account on this computer clears it too.
- **Relay reach and identity are worded in the user's terms**: "Also look on the relays that people I follow use" (on: "You miss fewer posts. Vega also connects to servers you did not choose, and each one can see your IP address."; off: "Vega only talks to your relays. Posts from people who publish elsewhere will not appear."), and "Prove who you are to: Only my relays / Any relay that asks". These live here only; Settings points here.
- Under a disabled "Discover relays", the true reason: loading, could not be loaded, or "Follow a few people first".
- `RelaysView.test.tsx` holds the split, the status words, Remove with Undo, the confirmed removal of what did not answer (and not of a connected relay), sharing and the unshared marker, and the wording.

## Notifications

Until October 2026 "Notifications" was mentions only, as bare note cards with nothing saying what had happened; zaps received and new followers lived under two other sidebar items, each with its own badge; a read item was dimmed to 50%, action row included, and any click on a card marked it read. Zap receipts the poller saved were already coming back from the DB and passing the view's `kind !== 3` filter, so a zap received while Vega ran showed up as an empty note card.

- **Four tabs: All, Mentions, Zaps, Followers**, each with `unread` for what still needs attention. The kind is read from the event (`notificationKind` in `src/stores/notifications.ts`): 9735 is a zap, 3 is a contact list that names you, the rest are mentions and replies.
- **Opening fetches all three** (`fetchNotifications`: mentions and zaps received from the last 7 days, and the contact lists that named you in the last 30 days), together, and saves each new event under its type, which is what the poller's "newest per type" reads. Before, only mentions were asked for on open; zaps and followers arrived through the 60 s poller alone, limited to since the newest in the DB or the last five minutes. Zaps take the mentions' window on purpose: without one, fifty receipts of any age came back unread on the first launch after the upgrade. Mentions that come back empty are asked for once more, on their own (gated on the whole sweep, the retry never ran for anyone with a zap). A fetch that throws is a failed load only when nothing else came back; with rows from the others it is shown as those rows. A sweep belongs to the account it was started for: after each wait it checks `currentPubkey` and drops its results if the account changed.
- **"New follower" is decided in one place, for both paths.** The sweep reads where the newest follower it knows of stands (the lists held, else the DB's newest `follower` row) before saving anything; a list newer than that from someone not yet among the followers held is a new follower (`addNewFollower`), whichever path found it. Before this the sweep saved followers without ever calling them new, and the poller, reading "since the newest in the DB", then found nothing: followers gained while Vega was closed never reached the badge. With nothing known yet (a first run) nobody is new, as for DMs. **A follower already held is not saved again** under the new id their edited list carries: a kind 3 is replaced on every edit, and those rows crowded mentions and zaps out of the DB's newest 500 and the startup load. **What the poller finds goes into the store** (`addNotifications`: by id, one list per follower, newest first, capped, recounted), or the badge learned of a zap only at the next open or restart.
- **A reason line above every item**: "Alice replied to you" (a kind 1 with an `e` tag), "Alice mentioned you", "Bob zapped you 21 sats", "Carol follows you". Present tense for followers on purpose: a kind 3 that names you says that its author follows you now, not that they started then (anyone who updated their list in the window appears). Under it, a mention is a `NoteCard`, a zap is `ZapRow` in `compact` mode (the reason line already says who, how much and when), a follower is `FollowRow` with `isNew`. Both rows moved to files of their own (`src/components/zap/ZapRow.tsx`, `src/components/follows/FollowRow.tsx`) and are shared with Zap history and People.
- **Seen by being looked at, not by being clicked.** What the open tab shows, in front for 1.5 s (`inFront` is the ui store's current view, since the view stays mounted behind Back), is marked read, and exactly that (`markReadMany`, `clearNewFollowers(people)`): not the other tabs, not what arrived after the moment began. An item that arrives while the view is in front joins the highlight and gets a moment of its own (the effect keys on the ids of what is shown and unread). What was new stays highlighted (`border-l-2 border-l-accent bg-accent/5`, and "New:" for a screen reader) until the view is left; the left border is always drawn, transparent when not highlighted, so rows do not shift. A read item has normal opacity. A click on a card opens the thread and marks nothing. "Mark all read" stays in the header while anything is unread, followers included.
- **One badge.** The sidebar's Notifications count is unread mentions and zaps plus the new followers (`unreadCount + newFollowerPubkeys.size`, the set the view reads, not a separate counter). Followers have no read state of their own: kind 3 ids change on every update, so "new" is this session's set. The account menu's People item and the account control carry no follower count any more; People reads "new" live from the same set.
- **Muting applies to who did it**: the zapper for a receipt (the author of the embedded zap request, which is what they signed; the receipt's `P` tag only as a fallback), the author otherwise. A zap from your own key is not a zap to you. The muted-keyword filter applies to mentions only.
- Empty states per tab, and a failed or unanswered fetch with nothing held on that tab says so; a follower held counts as a row for All and Followers and not for Mentions.
- **Known gaps.** A zap receipt is taken at its word: whether the embedded request is genuinely the zapper's, and whether the receipt comes from the recipient's LN provider (its LNURL `nostrPubkey`), are not checked, so a forged kind 9735 can read "Alice zapped you 1,000,000 sats" (true of Zap history before this, now more visible; `parseReceipt` says so). One `fetchOutcome` covers the three fetches, so when one of them throws while another returns rows, that one's tab reads as empty rather than failed (rare: `fetchWithTimeout` never rejects). "Carol follows you" comes from the newest list of hers that names you, which stays true in the DB after she unfollows, since `#p` queries never return her newer list. The 1.5 s moment runs while the window is in the background too. Keyword mutes do not reach zap comments.

## Back keeps your place

Before October 2026 only the feed stayed mounted. Every other view unmounted the moment a note, a profile or an article opened from it, so Back found a blank search page, the top of Latest instead of the seventh article in Following, the Notes tab instead of Articles, and a hashtag page asking its relays again. "Find, look, return" restarted from zero each time.

- **A list view Back can lead to stays mounted, hidden** (`KEPT_VIEWS` and `keptViews` in `src/stores/ui.ts`; `KeptView` in `src/components/shared/`): search, articles, bookmarks, hashtag, notifications, follows, zaps and media, plus the feed as before. "Can lead to" means the view is open or in the view stack. A sidebar click clears the stack (`setView`) and counts a `trip`, which keys every kept view, so the next visit starts fresh even when the destination is the view already on screen: Notifications chosen again from a thread opened out of it is a new list with its first load, not the old one at its old scroll. A sidebar destination is a new trip, Back is the way back from one.
- **Hidden means `display: none`**, as for the feed: out of the Tab order, away from screen readers, and `usePopoverDismiss` already treats a popover in a hidden view as gone. Focus held inside the view is let go as it hides: an engine that leaves focus on a hidden field sends every keystroke there, and Escape to the field instead of Back. Effects keep running; a list that refreshes itself goes on doing so, and a load that ends while the view is hidden lands in it. Mount-only effects do not run again on Back (a view's first load, a field's `autoFocus`): what should happen each time the view comes in front keys on the ui store's `currentView`, as Notifications does.
- **The scroll position is recorded as it happens and put back in a layout effect.** Browsers do not promise to keep a scroll offset across `display: none`. `KeptView` listens for scroll in the capture phase (scroll does not bubble), keyed by element, and restores before paint when the view is shown. Nothing to do per view. **Hiding is itself a scroll to 0 in Chromium's eyes**: the offset goes with the box and a scroll event follows a frame after the class changed (measured on a search page: "scroll 700", hide, "scroll 0"), so nothing is recorded while the view is hidden, by the prop or by anything above the list being `display: none`. Recorded, that 0 was what came back, while a list on the Articles view happened to survive, which is why one scenario is not a check. Best effort: it is a pixel offset, not the row, so a list that changed while hidden comes back near the place, not on it.
- **Each view has its own `Suspense` boundary.** One boundary around all of them hid the kept views with an inline `display: none` while a lazy view's code loaded, before the prop said so: the first thread of a session, opened from a scrolled search, lost the place.
- **The kept elements are made once** (module-level constants in `App.tsx`, `memo` on `HashtagFeed`), because App renders on every navigation and a new element each time renders every hidden list, and parses every note in it, on every click. For the same reason `NoteContent` and `ArticleCard` read the ui store through selectors, not `useUIStore()` whole.
- **The view-stack entry holds what the view needs to be itself again**: the note, the person, the article, and the hashtag. Back from a note to a tag's page showed whatever tag was opened last, because `pendingHashtag` was not in the entry. **Hashtag pages are kept one per tag** (`keptHashtags`): a single instance switching tags discarded one tag's rows for the other's and brought the other's offset back onto them.
- **Profile and thread are not kept.** Each has one slot (`selectedPubkey`, `selectedNote`), so a second instance would show the wrong person. The profile instead remembers the tab last open on each person for the session (`profileTabs` in the ui store, the newest two hundred) and opens on it; a remembered Articles tab asks for the articles at once, since they are what is showing. The thread still reloads.
- Verify in the running app, from a cold start (the lazy chunks matter): search, open the first thread of the session, Back; Articles on Following, scroll, open the seventh, Back; a profile's Articles tab, open one, Back; Notifications, a mention, then Notifications in the sidebar again. Watch WebProcess memory across a long chain of kept views on WebKitGTK: none of these lists is virtualised, and WebKitGTK does not evict decoded images.

## View header and tabs

Views start with `ViewHeader` (`src/components/shared/ViewHeader.tsx`), and a view that has tabs uses `Tabs` (`src/components/shared/Tabs.tsx`). Before October 2026 each view built its own: header heights from 45 to 133px, a "← back" link on one top-level view and no other, and tabs built five ways in five places. Clicking down the sidebar, the top of the window jumped on every view.

- **The header is 48px plus its border** (`min-h-12 box-content`, in both shapes, and the sidebar's header matches) and only grows when its contents wrap. They are allowed to wrap: a dense header in a narrow window must not push a control out of reach.
- **A top-level view's title is the sidebar's label, word for word.** "People", not "Follows". "Write Article" for the drafts list. If a sidebar label changes, the title changes with it. The feed is "Home" in the sidebar and has no visible title (its tabs are the title); People and Zaps have left the sidebar for the account menu and keep their titles.
- **Back appears only on a view reached from another view**: a thread, a profile, a hashtag, an article, a podcast's page. A view opened from the sidebar has none. `setView` clears the back stack, so a Back there could only ever lead to the feed.
- **Slots**: `onBack`, `title`, `meta` (quiet text such as a count or a status) form one group that stays on a single full-height line. `tabs` is for the feed, in the title's place. `children` is a field that takes the free width (the search box). `actions` are the controls at the right edge. Pass content to a slot; do not build a second bar under the header for what a slot can hold. A slot given `null` or `false` renders nothing.
- **A header with no visible title still has one**: pass `hiddenTitle` (the feed, search), so the page has a heading for someone who cannot see the tabs or the field.
- **Tabs in a header never shrink, and the controls wrap above them.** In a narrow window the feed's tabs were squeezed to nothing and drawn *under* the controls beside them: a flexible box with a minimum width of zero does not wrap, it overflows. The `tabs` slot is `shrink-0`, and a header with tabs uses `flex-wrap-reverse`, so the controls go to a line above and the selected tab's underline stays on the divider. Check a header change at 700px wide with the sidebar at 300px, and test for overlap between every pair of controls, not for controls outside the header: overlapping controls are all still inside it.
- **Controls beside tabs must not change width as the view loads.** The feed's "updated" time is always rendered at a fixed width and Refresh keeps its label while it loads, swapping its icon for a spinner of the same size. When they appeared and grew, a header near its wrap point went from one line to two as a load finished, and the tabs moved just as someone reached for them.
- **Tabs are the first row under the header, left-aligned, in Title Case.** The feed is the one exception. `Tabs` knows it is in a header from context (`TabsInHeader`, set by the `tabs` slot); there is no prop to keep in step.
- **A number on a tab is `count` or `unread`, never part of the label.** `count` is a total (results found, people followed), drawn quietly. `unread` is how many still need attention, drawn as a badge and named "unread" to a screen reader. Bookmarks showed unread articles as a quiet total under "12 saved", which read as three saved articles. Pass `undefined` for none. A list that has not loaded has no count: "Following 0" before the follow list arrives is a false statement.
- **`Tabs` is a real tab list.** One tab is in the Tab order: the selected one, or the first usable one when the selected tab is disabled or missing (Articles on Following, then sign out). Arrow keys, Home and End move focus and do **not** select, because selecting loads; Enter, Space or a click selects. Keys with a modifier are left to the app.
- **Give tabs a `panel` id and spread `tabPanelProps(panel, value)` on the content they switch**, so a screen reader can go from the tab to what it controls.
- **Not on the shared header, on purpose**: the article editor (a writing surface: its bar holds a Drafts button, the save status, Write/Preview and Publish), the conversation bar in Messages (a person, not a view), and the onboarding screens. The emoji picker's groups and the onboarding login's segments are tab-like but are compact controls inside a popover or a form, not a view's tabs.

## What counts as published

"Posted." is true only if a relay on the network has the note. Until October 2026 it was also said when the built-in relay alone had it.

- **Every publish goes through `publishToNetwork(event, relaySet?, timeoutMs?)`** (`src/lib/nostr/core.ts`). Never `event.publish()` by itself, and none of NDK's shortcuts that publish (`react`, `repost`, `publishReplaceable`). `publish.test.ts` reads the source for it. The wallet connection is the one exception: it has an NDK of its own, with no built-in relay in it.
- **NDK's own publish waits until every relay in its set has answered or run out of time, and succeeds if one of them accepted.** Its set is worked out per event (the author's write relays, relay hints in the tags, relays of the people tagged) plus every relay of the user's that is connected right now. With the network gone, what is left of that is the built-in relay alone. Shown with real NDK: the publish resolved in 8 ms, with the built-in relay as the only relay in the set and the only one that had the note. "Posted.", "Relay list published." and "Following …" were then said of something only this computer had, and a follow or a profile edit made offline looked done.
- **The network first, the built-in relay's copy afterwards.** Not both at once: an event the built-in relay holds and nobody else does shows up in the user's own feed as if it had been posted, and a second try makes a second event beside it. The copy is best effort and goes straight to the relay. If it fails, the catch-up sync at the next start brings back the user's notes, profile and follow list, and nothing else: a reaction, a repost or a list whose copy failed is simply not on the built-in relay.
- **When nothing in NDK's set is connected, the user's own relays are tried as well** (`ownNetworkRelays`): NDK connects to publish, and gives up after its usual two and a half seconds per relay. "Own" is every relay in the pool that is not the built-in one, and is either in the user's list or was never held on a timer in this session to read someone else from (the relays NDK added from the user's published relay list). Taken from the pool as it is, never built from stored URLs: that would open sockets of its own and could reconnect a relay the user removed.
- **A relay in the user's list is theirs whatever NDK's timers say.** NDK never takes a relay off its list of borrowed ones (`temporaryRelayTimers`, private, read through a cast), and leaves a relay on that list out of the set it works out for a publish. A relay it once held to read a follow from, and which the user then added, was not published to at all, and with no other relay the built-in one's yes was taken for "Posted.". Both the fact and the fix are in `publish.live.test.ts`.
- **The built-in relay's word counts when it is the only relay the user has.** Relays that are merely down do not make it the network. For reads the same question is asked of the whole pool (`heardFromNetwork`, in the lists section).
- **"The built-in relay" is a relay at a local address that is not in the user's list** (`builtInRelayTest`). One that is in the list is theirs: their own strfry, or the local end of an SSH or Tor tunnel to a relay elsewhere. `isLocalRelayUrl` alone takes it for the built-in one: for the list states its answers did not count. The other uses of `isLocalRelayUrl` (relay liveness, the contact list, the relay badge, `isRelayAllowed`, the AUTH scope) still read any local address as the built-in relay.
- A publish that reaches nobody throws NDK's own "Not enough relays received the event…", which `explainPublishError` already words. Callers need no second case.
- **A publish that "failed" on the time limit can still arrive.** A relay that wants AUTH first answers `auth-required`, NDK keeps the event and sends it again once signed in, and with a remote signer that is later than two and a half seconds. The built-in relay's instant yes used to hide this. A second press then makes a second note. Messages use a fifteen-second limit for this reason (#53). Notes do not yet.
- **Vega queues nothing for later.** The built-in relay syncs from the network, never to it. A note written offline stays in its box with the error, as it does when the built-in relay is off. Sending it once the relays are back would be a feature of its own.
- **A message is sent when the recipient's wrap is out** (`sendDM`). The sender's own copy is a second event, and when only that one fails the message is reported as sent, with a warning that it will not show in the conversation. Reported as a failure, the box kept the text and a second press sent the message twice.
- **A list that is "cloud wins" needs a record of what this device changed.** The podcast list is replaced by the relays' copy at each start. A change whose publish failed was thrown away by that, silently. `podcast.ts` keeps, per account, which shows were changed here (added or removed) and are not yet on a relay. This device's list decides for those shows and the relays' list for all the others.
  - **Record which, not when.** A time has to be compared with a relay event's `created_at`, which is another device's clock, and cannot say what to do when both sides changed. "This device changed X and B" can be applied to any list, any number of times.
  - **One way in and out (`reconcile`): read the relays' list, work out the result, publish it.** At the start, a moment after a change, and from "Try again". A change is not published from what this device happens to hold: it used to be, over whatever another device had done since, and over the relays' list altogether when the start had not managed to read it.
  - **The read says found, none or unknown (`fetchPodcastList`), and only the first two are acted on.** Each of the user's relays is asked on its own, because one fetch over several is cut short by NDK and a list held only by the slowest then reads as none (the contact list section). "None" takes every relay that is connected answering: a relay that is down is not asked, as for the contact list. Unknown takes nothing and publishes nothing; after a change it is said, with Try again.
  - **The built-in relay is not asked what the relays hold.** It has this device's own last publish and answers at once with the network gone. Taken for the relays' list, a change was published on top of it, and what another device had done since was undone (reproduced with real NDK, now in `publish.live.test.ts`). It is asked only when it is the one relay the user has.
  - **One round at a time (`inTurn`).** Two rounds at once can each publish what they worked out from the same reading, and a reading asked before another round's publish holds the list from before it. The publish has a time limit, so a signer that never answers does not hold up every later change.
  - **A publish that went out clears the record only if nothing was changed while it was on its way**, and only if something did go out: `publishPodcastList` returns false with no key of that account's to sign with.
  - **An empty list is not "no list".** It is a list someone emptied, and is taken as it is.
  - Still open: a list found on one relay is acted on although another relay, which did not answer, may hold a newer one. And a relay that is down may hold the only list, so "none" can still be wrong, and this device's list published as the first one over it. And what is subscribed to while signed out is taken over by the first account that has no list of its own on this device.
  - Any list that takes the relays' copy over this device's needs the same before its publish may fail quietly.
- **Vega's own subscriptions ask for no optimistic copies** (`skipOptimisticPublishEvent`: `fetchWithTimeout`, `fetchFromRelay`, the gift-wrap fetch, the feed's live subscription). NDK's own reads still take them: `ndk.fetchEvents` in search, and `user.fetchProfile()`. NDK hands an event to every open subscription it matches the moment it is published, before any relay has answered. A reply no relay took was in the thread's replies that were loading, a note appeared under "1 new note", and either counted as a relay having answered.
- **A relay removed from the list comes back on the next publish while the user's published relay list still names it.** NDK adds the author's write relays to its set, for good. Older than `publishToNetwork`, which only follows NDK's set here. Removing a relay is not finished until the relay list is published.
- Verify with `publish.live.test.ts`: two `nak serve` relays, see its header. What NDK reports as published is NDK's to decide, so a stand-in for it is not evidence. The test asks the relays themselves what they hold.

## Toasts, and saying what happened

Before the October 2026 UI review the toast channel carried relay events and little else. After Follow or Mute from a note's menu, a quote, a comment on an article or a post made from Trending, nothing on screen had changed. A thread reply, a bookmark, a mute or the relay list that failed to publish failed in silence.

- **Say it worked when nothing else on screen does. Say it when it did not.** That is the rule for when to raise a toast. A button that changes where it was pressed is its own confirmation: Repost turns green, the bookmark fills, Follow becomes Following, a reply appears in the thread. A second "Reposted" in the corner is noise. A menu item that closes its menu, a dialog that closes itself, and a note the list on screen will not show change nothing, so they get a toast. The second half is not yet true everywhere: see the gaps at the end.
- **`addToast(message, type, options?)`** (`src/stores/toast.ts`). The third argument is a duration in ms or `{ autoCloseMs, sticky, action, key }`. Types: `success` and `info`; `warning` for something degraded that is not about what the user just did (the connection dropped, a relay refused Vega's sign-in); `error` for "the thing you just did did not happen".
- **Durations follow from the type** (4 s, 4 s, 6 s, 8 s) when none is given, and a toast with an action then gets at least 8 s.
- **A toast's clock runs only when nothing says it must wait**, and starts over from the beginning when the last reason is gone.
  - *Focus inside it* holds that toast alone (`holdToast(id, "focus")`). It is a reason of its own: with one flag for pointer and focus, the pointer leaving started the clock with focus still on "Undo".
  - *The pointer over any toast* holds the whole stack (`holdAll("pointer")`). The oldest toast is at the bottom: when it left, the ones above dropped a slot under the pointer and the press meant for "Undo" landed on a neighbour or on the page. A toast removed under the pointer sends no "leave", so the container lets go when the pointer is next seen outside the stack, moving or pressing, and the store lets go by itself when the last toast leaves. **The store is told in the pointer handlers, not from an effect on state**: an enter and a leave handled before React renders again never show up as state, and a hold taken in one place and released in the other would be kept for good.
  - *A window that cannot be seen* (`document.hidden`) stops every clock. *A window that only lost the keyboard* stops the clocks of failures and of toasts with an action, and no others: it may be in full view as a tile beside a terminal, and "Link copied." sat there for as long as the user typed elsewhere. A pointer or key event in the window counts as being back, for a webview that never reports focus returning. Only the clocks a change of window stops or starts are touched (`waitsFor`): restarting them all gave a plain toast a fresh four seconds every time the keyboard changed window, which with focus-follows-mouse is every time the pointer crosses an edge.
  - A held toast is not restarted when it is said again.
- **Five toasts at most, and which one goes is decided in `spareIndex`.** Never one that stays until dismissed: five ordinary toasts pushed the keychain warning out, and with it the only button that copied the key. Then a plain message before a failure or one with a button, a free one before one somebody is reading, the oldest first, and never the one just raised. With nothing that may go, the stack is allowed to be longer. Nobody is pushed out while the pointer is in the stack, for the same reason it is held; the stack is trimmed when the pointer has left.
- **A toast that is no longer true is taken down** (`removeByKey`): "couldn't publish your mute list" when the list goes out with the next change, the key warning when a later sign-in saves the key or the account is removed, "Connection lost" and "Resetting relay connections" when "Back online" is said (`startConnectionMonitor` in `feed.ts`, keyed `CONNECTION_LOST` / `CONNECTION_RESET`; "Connection lost" is sticky until then, since reconnecting is what it is waiting for).
- **A relay's `auth:failed` carrying "Relay <url> disconnected" is not a refusal** (`looksLikeDisconnect`): the socket went before the relay answered, which every `resetNDK` does to every relay, and the notice blamed the relay for Vega's own reconnect. It says nothing and keeps the relay's one notice for a real refusal.
- **One action at most**: Undo, Try again, View, or the name of the view where it can be dealt with (`openView("relays")`, so the relay layer does not import navigation). A message that needs a decision is not a toast, because it disappears. The one exception is `sticky: true`, which stays until dismissed: the keychain warning below.
- **Two toasts with one `key` are one toast**, with the newer words and action and its time started over. The key defaults to the message. Give a key to a toast with an action whose words are not unique: two failed reposts say the same sentence, and merged on it "Try again" retried only the last. `repost:<note id>`, `follow:<pubkey>`, `mute:<pubkey>`, `publish:mutes`, `posted:<note id>`.
- **An action belongs to the account that did the thing, and so does the toast.** Build the action with `forThisAccount(label, run, account)` (`src/lib/toastActions.ts`): pressed under another account it does nothing and says so. The signature would be the current account's, whoever asked: Undo after a switch unfollowed for the wrong person, and "Try again" on a failed repost reposted as them.
  - **Read the account before anything is awaited, and pass it in** (`currentAccount()`, `src/lib/currentAccount.ts`). A publish takes seconds. Read afterwards, "the current account" is the new one, and it was handed an Undo for what the old one did.
  - **If the account changed while it was on its way, raise nothing** (`stillAccount(account)`): not the success, not the failure. It was not the new account's to hear. `tellPublish` does this itself. A follow whose publish fails after a switch ends as `"dropped"`, not `"failed"`, and leaves the new account's list alone.
  - Toasts made with `forThisAccount` are dropped when the account changes (`dropAccountToasts`, from a `subscribe` in the user store). "View", "Relays" and the key warning are about no account in particular and stay.
  - The same goes for a publish that waits. The mute and bookmark lists go out a second after the last change: the account is read when the change is made, and a list is not published at all if someone else is signed in by then. It would replace their list with this one. A batch of changes belongs to one account too: an unmute by the account before must not word the failure of this one's mute.
  - Stores that the user store imports cannot import it back, which is why the current account is kept in a leaf. Use the leaf, not the store, for these checks, so there is one answer to "who is signed in".
- **Do not put a component's own handler in a toast's action.** Feed rows are virtualised: the row may be gone when the toast is pressed, and its closure holds that render's state. Reposting lives in `src/lib/repost.ts` for this reason, and takes only the account and the note. A failed reaction offers no "Try again" at all: the emoji is one press away, and the retry ran an old render's idea of what had been reacted with and sent the reaction twice.
- **Follow and Mute from a menu go through `setFollowing` and `setMuted`** (`src/lib/socialToasts.ts`), which say what happened and offer Undo. `follow` and `unfollow` in the user store return how it ended (`"done" | "failed" | "dropped"`), and the helper goes by that. It must never look at the list afterwards: after a failed publish the list is put back to what the relays hold, which may already have the person, and "Following Carol" then appeared beside "Couldn't publish your follow list".
- **Muting and bookmarking take effect on this device whatever the relays do**, so their toasts are about the publish alone, and say which kind of change it was. A mute that could not be published "is on this device only". An unmute, or a removed bookmark, "may be undone the next time your list is loaded", because loading merges the relays' list back in. Both lists are published once for changes made within a second. "Try again" publishes the list as it stands at that moment and says so when it works: the toast is gone by then and nothing else changes. `publishMuteList` and `publishBookmarkListFull` return whether anything went out: with no key to sign with they return `false`, "published" is not said, and a retry that ends that way says why instead of closing its toast in silence.
- **A publish that only needs a toast goes through `tellPublish(run, { done?, kept, view?, verb? })`** (`src/lib/publishFeedback.ts`): replies in a thread, a comment, a like or repost on an article, a poll vote, the relay list. A failure is always said. `done` is said on success, and left out where the result shows by itself. `view` adds "View" for a result that is a note, and keys the toast by that note, so two comments in a row are two toasts that each open their own. It never throws and returns `{ ok }`.
- **A failed publish is worded by `explainPublishError(err, kept, verb?)`** (`src/lib/publishErrors.ts`), in a toast or inline. `kept` says what became of the work: "Your reply is still in the box." Never show `Failed: ${err}`: it reads "Failed: Error: Not enough relays received the event (0 published, 1 required)".
- **Show a result after it has gone out, not before, unless it can be taken back.** A poll vote was drawn as cast at once and stayed that way when no relay took it: the poll then showed results and the vote could not be tried again.
- **Something on its way is shown as on its way, and claimed outside the component.** A poll option says "Sending…" and the others are held back (`aria-disabled`, never `disabled`, which drops keyboard focus to the page). The claim is `beginVote`/`endVote` in `usePollVotes.ts`, a map beside the cache: a row that scrolled out and back, or the same note open in a thread, is another component, and a ref inside one let a second vote through.
- **A poll vote has a time limit** (`withinTime`, `src/lib/timeLimit.ts`). A remote signer nobody approves never answers, and the poll stayed dead for good. The work is not stopped by the limit: if it goes out after all, it is shown then, because the relays have it. That makes two votes that can finish in either order, so votes are numbered as they are cast and the one shown is the one cast last among those that went out (`takesTheVote`): that is the one the relays count. Reposts, replies and messages have no such limit yet (see the gaps).
- **A hook that records a result must write it where an unmounted row can find it, and tell every row that is showing it.** `useReactions` and `usePollVotes` wrote to their cache inside a state updater, which React never runs for a row that has scrolled out of the virtual list. The row that scrolled back showed no pill and offered the same reaction again. `usePollVotes` keeps a set of watchers per poll for the second half.
- **A result that arrives must not undo what happened while it was on its way.** The tally of a poll is asked for before a vote goes out and does not contain it: it replaced what was shown, and the poll offered the vote again. A vote cast in this session wins over whatever the tally holds, an older vote of ours from another device included. The same for a reaction and its tally (kept in the cache whether or not the row is still mounted, and through a batch that fills the cache in), and for a reply sent while a thread's replies were loading: the thread view keeps the replies published from it and adds them to the list that arrives. In the other order, when the list arrives while the reply is on its way, the reply is added to the tree as it is then (`setTree` with a function), not to the tree of the moment Reply was pressed. A reply that goes out after another note was opened is not that note's. A read of a message thread started before a second message was sent came back last and took that message off the screen. None of this can lean on NDK handing our own event to a fetch that is on its way: fetches no longer take those (see "What counts as published").
- **Reads that can overtake each other are numbered** (`reads` in `ThreadPanel`, `DMView.tsx`). A read sets the list only if none started after it has done so already, and loading ends when a read has been shown or none is left that could be. "Only the newest read counts" is not enough: the newest can fail while an older one still holds the answer, and a loading flag that follows one read sticks when another overtakes it.
- **One panel per conversation, by `key`.** A single `ThreadPanel` for all of them kept the text typed for one person in the box for the next, and a send that finished after a switch ran in the old render's closure: it put the old conversation's messages under the new one's name and emptied the new one's draft. Anything with a draft or an action in flight that belongs to one subject gets a key for that subject.
- **Keep "it was sent" and "the list was read again" in separate `try` blocks.** In Messages the re-read of the thread sat in the send's `try`. When it failed the box was already empty and the message was out, and the error said "Couldn't send… still in the box". It was sent again.
- **Other people's words get a length limit in a sentence of ours**, through `clipText(text, max)` (`src/lib/utils.ts`): a display name in "Muted …" (40 characters), a relay's or signer's error (90 to 140). It counts with `Array.from`, not `.length`: a cut through the middle of an emoji leaves a broken glyph. End the clause with `endSentence`, which adds a full stop only when the words did not bring an ending of their own: not "slow down….".
- **Copy through `copyText(text, done?)`** (`src/lib/clipboard.ts`). It returns whether it worked, and says so itself when it did not. Pass `done` where nothing beside the button changes. A button with its own "Copied" sets it only on `true`: three places showed "Copied" without waiting, one of them for a secret key.
- **A key the keychain would not store is said in a sticky toast that copies the key itself, and names the account**, because it outlives an account switch. It used to say "Copy your key now from Settings" and vanish after twenty seconds, and Settings read only the keychain, which is exactly where the key was not: there was no key row to copy from.
- **Read a secret key back through `readSecretKey(pubkey)`** (`src/stores/user.ts`), never `load_nsec` directly. It returns the keychain's copy, or the one this session's signer still holds. Settings then shows the row with a warning, and the remove-account dialog can still copy the key. Without the fallback, closing the warning left no way to the key at all.
  - `stored` has three values. `false` only when the keychain said "no entry" or a write failed in this session. `null` when the keychain could not be read: a locked one may well hold the key, and "not saved" would be a guess. Settings words the two differently.
  - **The warning toast does not hold the key.** Its "Copy key" reads it when pressed, so a toast that outlives its account has nothing to copy.
  - **Removing an account drops this session's copies too** (`_signerCache`, `_nip46SignerCache`). "This deletes the secret key stored on this computer" was not true until Vega closed: the signer stayed in memory, `switchAccount` would sign with it again, and with the fallback above Settings would have shown the key of an account added back read-only.
- **The toast stack is drawn on every screen, onboarding included** (`App.tsx`). Onboarding is where a key is first copied and first stored, and its toasts went to a stack nothing drew.
- **Toasts render at `<body>` through `BodyPortal`, above dialogs (`z-[60]`).** Inside the text-size zoom, so they grow with the text. Above a dialog's backdrop, or a failure raised while a dialog is open sits dimmed under it. The stack starts above the podcast player bar when that is showing, takes no clicks itself (`pointer-events-none`), and draws the newest toast on top so that the one being reached for does not move.
- **What a screen reader hears comes from two regions that are in the page from the start**, one polite and one assertive (errors), whose text changes. A toast inserted with `role="status"` and its text already in it is often not announced. The visible toasts carry no live role, so their buttons are not read out as part of the message. Each kind has an icon and a word ("Error:"), not only a colour.
  - **Each toast is written to its region once, when it is raised or said again** (`said` on the toast counts). Never work the text out from what is left on screen: derived that way, the region changed back to an older toast whenever a newer one left, and the older one was read out a second time. Toasts raised in one go arrive in one render and are written together.
  - The same words twice are no change to a live region and are not read. A zero-width space is added to make them one.
  - The stack is a named region (`role="region"`) only while there is a toast in it. An empty landmark is one more stop on the way through the page, to nothing.
- **F6 moves focus to the newest toast**, from anywhere, a text field or a dialog included. In Tab order the stack is after everything else on the page. Escape with focus in a toast dismisses that toast (it is a layer, see the dialogs section), and focus goes back to where it came from. In a toast that stays until dismissed, Escape only gives focus back: a stray press must not put away the key warning. The layer exists only while the focused toast does: one taken away by the store with focus inside left a layer that swallowed every later Escape. "Where it came from" is the element focus left on its way into the stack. Coming from nowhere (F6 with nothing focused) there is nowhere to go back to, and focus is taken out of the toast all the same. A window reports no "where from" either when it gets the keyboard back, so a blur to nowhere with `document.hasFocus()` false is remembered as a trip to another window, and coming back into the same toast keeps the place.
- **A click on a toast goes through an open popover's outside-click handler** (`usePopoverDismiss`): the menu closes and the toast's button is pressed, in one click.
- **A bar pinned to the bottom of a view tells the stack to start above it** (`useToastFloor`, `src/hooks/`): put the returned ref on the bar. Send in Messages is in the corner toasts are drawn in, and a relay's sign-in warning, which opening Messages raises, sat on it for twelve seconds, or for as long as the pointer rested there. The hook publishes the bar's layout height as `--toast-floor` and follows it as the message box grows. Layout height, not a measured rectangle: the bar and the stack are under the same text-size zoom (see the action row section on rects and zoom). The podcast player bar keeps its own rule in the stack's classes, because it is outside the zoom and never changes height.
- **React reports "the pointer left to nowhere" as the window, which is not a node.** `element.contains(e.relatedTarget)` throws on it. Check `instanceof Node` first.
- **Known gaps.**
  - Still silent when it fails: sharing a podcast episode.
  - Still shown raw: a zap that fails (the wallet's own message), and image uploads (`Upload failed: Error: …`).
  - **Value 4 Value counts a payment whose request went out** (`PayOutcome` in `src/lib/podcast/v4v.ts`): "paid" when the wallet confirmed, "sent" when it did not answer within NDK's 30 s (`NwcTimeoutError`), which is counted and shown as "sent, not yet confirmed by your wallet"; the sats had left while the counter said zero. A request no relay took, a wallet that refused, or an address that gave no invoice is "failed": not counted, named on the dashboard (`lastFailure`), and said in a toast once per episode and recipient. Bare `requestEvent.publish()` in `nwc.ts` now rejects the wait when nothing took it, so a publish failure is not mistaken for a slow wallet.
  - A reply containing one of the user's own muted words is filtered out of the thread it was posted to, with no toast.
  - A toast said again with the same key is read out again but does not replay its entrance.
  - The live regions keep their last text, so it can be read again in browse mode. A toast that outlives onboarding (the key warning) is written a second time when the main window takes over, because that is a second container.
  - Reposts, replies and messages wait for a signer without a time limit. A remote signer that never answers leaves the button busy.
  - `useReactions` writes its cache where an unmounted row can find it, and keeps a reaction given while the tally was on its way, but does not tell other rows showing the same note. `usePollVotes` does.
  - A mute or bookmark made in the second before an account switch is kept on record for that account and goes out at its next start; nothing says so at the time.
  - The cache behind `usePollVotes` is per poll, not per account. A vote shown for one account is shown for the next until Vega restarts. Older than the toasts.
  - A screen reader that treats everything outside an open `aria-modal` dialog as inert may not announce a toast raised while one is open.
  - Not rendered in a test: the article view's like, repost and comment, the relay list button, and the toast stack during onboarding. Each is a call to a tested helper.

## Lists: loading, empty, unreachable, failed

Before the October 2026 UI review most lists did `fetch().catch(() => [])` and showed their "nothing here" sentence for whatever came back. A relay that never answered and a relay that answered "nothing" looked the same: "No notes found", "No bookmarked notes", "No zaps received yet", "No results". To someone with a year of posts that reads as data loss. Bookmarks said "No bookmarked notes." under a header that said "2 saved".

The aim is that a list says "empty" only when a relay said so. The mechanism below gets most of the way there and errs towards "empty" where it falls short. The gaps are listed at the end, so nobody takes the aim for a guarantee.

- **A list with no rows shows a `ListState`** (`src/components/shared/ListState.tsx`). Four states, and it never shows the empty sentence for the last two: `loading`, `empty`, `unreachable` (nothing came back and the network did not answer) and `error` (the load threw). Those two are an alert with a "Try again" button. Do not write another empty-state block.
- **`fetchMark()` before the load, `wentUnanswered(mark)` after it** (`src/lib/listLoad.ts`), and only when the result is empty. `fetchWithTimeout` records every fetch in two totals (`src/lib/nostr/fetchTotals.ts`): fetches the network answered and fetches it did not. "Unanswered" means at least one fetch ended without an answer since the mark and none was answered. One answer from anywhere in the app in that time means relays are reachable, and the empty result is taken at its word.
- **One relay's EOSE is an answer, even when NDK did not end the subscription.** One relay of two is not NDK's quorum, so such a fetch runs to its timeout with zero events. The totals read `sub.eosesSeen` and count it as answered. The silent-pool streak (#65) counts the same fetch as unanswered and calls the pool silent after three, which is why **lists do not ask `isPoolSilent()`**: a list that did said "couldn't reach your relays" of a relay that had answered every time. The streak decides whether to reconnect. The totals decide whether a list may say "nothing here". Neither is derived from the other.
- **The built-in relay's answer does not count as the network's, unless it is the only relay in the pool** (`heardFromNetwork` in `core.ts`). It is on this machine and answers at once with the network gone. "The only relay" is decided from the whole pool, connected or not, as `ensureConnected` does, and **not from where NDK sent the subscription**: for a filter with authors and no outbox data NDK asks the relays connected right now, which with the network down is the built-in relay alone. Read that way it was "all that was asked" and was believed, and a profile's notes came back "answered" in 6 ms with every remote relay unreachable.
- **For a list loaded once per view, use `useLoadedList`** (`src/hooks/`), or `loadList` outside React. It returns `loading`, `loaded`, `unreachable` or `error`, and can ask a second time after an empty answer (`retryEmptyAfterMs`). What it returns always belongs to its current `deps`: a result is stored with the deps it was loaded for and compared during render. Clearing rows from an effect leaves one render with the new subject and the old rows.
- **A list that keeps rows across refreshes records a `LoadOutcome`** (`"pending" | "answered" | "unreachable" | "error"`) beside the rows: the feed store's `outcome` for Global and Trending, component state in `Feed.tsx` for Following, `fetchOutcome` for notifications, `listOutcome` for the bookmark list. It starts as `"pending"`: a list that has not been asked yet is loading, not empty. Global's first load waits for the relays to connect, and until then the tab said "No notes to show."
- **`stateWithoutRows(loading, held, outcome)` picks the state.** `held` is how many rows the list holds that this view could show, before the user's own filters. With rows held and all of them filtered out (mutes, the script filter) the list is empty for this user. Do not count rows the view never shows: when Notifications listed only mentions, the follower events the store also holds counted as "rows held", and an unanswered fetch read "No mentions yet." (Followers are rows of their own now, on All and on their tab, and still not on Mentions.)
- **A refresh that goes unanswered or fails leaves the rows where they are.** The Following tab replaced its notes with the empty result, and Trending emptied itself before asking, so a feed that had loaded went blank and said there was nothing. The feed now says so in a line above the tab ("Couldn't reach your relays, so this may be out of date."), whenever the tab holds notes, shown or filtered out. With none held, the list says it. An unanswered Global refresh does not move the "updated" time in the header.
- **Rows kept "from before" must belong to what is on screen now.** Keeping rows is what made this matter: the articles view has two tabs over one list, and Latest's rows were kept under Following, where the laxer filter also showed the spam Latest hides. Its rows, loading flag and outcome are stored with the tab and follow list they are for and read during render. The Following tab's notes are cleared when the account changes, because the feed is never unmounted, and only its newest load may land.
- **A list that needs the follow list shows `followListState(followsStatus)` while that list is empty.** Only `"loaded"` means the account follows nobody (see the contact list section). The Following tab (when it has no notes to show), the Following tab of Articles (in place of any rows) and People use it.
- **Search relays have connections of their own** and do not go through `fetchWithTimeout`, so `searchFetch` reports to the same totals with `recordFetchOutcome`. Anything else that fetches outside `fetchWithTimeout` and fills a list must do the same, or its list will say "nothing" with the network gone. Search says "No relay answered this search.", not "your relays": the relays a text search goes to are not the user's.
- **Bookmarks tell these apart**: the list not read yet, the list unreachable or failed, nothing saved, saved and nobody answered, saved and the relays returned none of them ("2 saved, but your relays did not have any of them.", the one case where something may really be gone), and saved items that were found and are articles, which are listed under the other tab.
- **No count beside a list that could not be read.** Not "0 saved", "Followers 0", "0 notes" or "0 in, 0 out" next to "couldn't reach your relays".
- **Tests play the relays through the real totals**: `recordFetchOutcome(true)` inside a fake fetch is "a relay answered", `(false)` is "nobody did". Do not stub `fetchMark` or `unansweredSince` with a copy of their logic. `fetchTotals.live.test.ts` runs the counting against real NDK and two `nak serve` relays, and is the test that fails if either of the two NDK facts above is forgotten. The unit test's stand-in once agreed with the code about a case NDK decides differently.
- **Messages already had this** (#65) and keeps its own wording.
- **Known gaps.**
  - NDK ends a multi-relay fetch early (see the contact list section), and what only the slowest relay holds is dropped. Every other relay did answer, so the list says "empty". Seen on 2026-10-12: the same account's zap history showed a zap in one run and "No zaps received yet." in the next.
  - The totals move when a fetch ends, not when a relay spoke: a fetch that collected events before the network went and timed out afterwards counts as answered then. They are also shared: a fetch answered by relays this list never asked still counts. Both make a list say "empty", not "unreachable".
  - Rows from the built-in relay alone are shown as loaded. With the network down and that relay on, a Following refresh replaces the notes with what it holds and says nothing about being out of date.
  - A note search asks the search relays for text and the user's relays for the hashtag: if only one of them answers, the result is "No results" although half the search was not carried out.
  - Not converted: the suggestions and the "No people found" hint in Search, relay recommendations in Relays, and the older-notes loader at the bottom of the feed.
  - Notifications, Articles and Bookmarks have no "may be out of date" line: a failed refresh with rows on screen says nothing.
  - A relay that answers `CLOSED auth-required:` never sends EOSE, so a pool of only such relays reads as unreachable.
  - The silent-pool streak itself still counts one relay of two as unanswered. That is #65's code and was left alone here.

## Dialogs, popovers and the keyboard

Before October 2026 eleven things floated over the page and closed in at least six ways. Escape closed one dialog from anywhere, one only while its text field had focus, one only while focus was inside it, and one by accident through the app-wide handler, which also changed the view behind it. In the feed a dialog covered one note instead of the window. The rule now: **Escape closes whatever opened last and nothing else, a click outside a menu closes it without doing anything else, and focus goes back to where it came from.**

- **Everything that floats is a layer in one ordered list** (`src/lib/layers.ts`), and one `document` listener decides Escape and Tab for all of it. Each floating thing used to add its own listener. Listeners on one node run in the order they were added, so Escape closed whatever had opened *first*: with a note's menu open and Help opened over it, Escape closed the menu underneath. A popover joins through `useEscapeToClose`, a modal through `useModal`. Do not add another `keydown` listener for Escape.
- **A layer keeps its place from when it opened.** `useEscapeToClose` adds it when `enabled` turns true and reads the newest `onClose` from a ref. Re-adding it on every new callback would lift an old menu above a dialog that opened after it.
- **A modal dialog is a `Dialog`** (`src/components/shared/Dialog.tsx`): zap, quote, login, help. It brings the backdrop, the panel, the title and the close button. Do not build another backdrop. The image viewer is the one other modal and shares `useModal` (`src/hooks/useModal.ts`).
- **Tab is kept inside the newest modal from `document`, not from the dialog.** A trap that listens on the dialog hears nothing once focus has fallen to `<body>`, and it does: the Zap button unmounts when pressed, a backdrop press that keeps a half-written quote leaves focus on the page, and the viewer's Next button disappears on the last image. From there Tab used to walk the sidebar behind the dialog.
- **Focus moves in, and goes back.** On opening it goes to a field that asked for it, else the first field, else the panel itself: never the close button or the main action, where a stray Enter would act. On closing it returns to what had focus when the dialog opened. A dialog opened from a menu item passes `returnFocus`, because the item is gone by then: Quote names the Repost button, "Add account" names the account arrow. If the opener is gone and another modal is still open underneath (signing in from the zap dialog removes "Sign in"), focus goes to that modal, not to the page.
- **The opener is read during the first render, not in an effect.** By the time an effect runs, a field with `autoFocus` already has focus and the opener is forgotten.
- **Because a dialog focuses its first field, a field must not change anything on focus alone.** The zap dialog's custom-amount field switched to "custom" on focus. Once dialogs took focus, every zap opened with no amount and a disabled button. Typing chooses; focus does not.
- **A backdrop press closes a dialog only if the press began on the backdrop.** Selecting the text in a field and letting go outside the panel ends as a click on the backdrop. And pass `closeOnBackdrop={false}` while something would be lost: a half-written quote, a typed zap comment, a payment in flight whose result is shown nowhere else. Escape and the close button still close it.
- **Inside a dialog, never size anything in `vh` or `vw`.** It renders at `<body>` through `BodyPortal`, inside the text-size zoom, where `85vh` came out as 121% of the window at Extra Large text and the title and last button could not be reached. The panel is limited to a share of the backdrop (`max-h-full`), and the viewer's picture to a share of the viewer (`max-h-[90%]`). Measured in Chromium; check a tall dialog at Extra Large text in the real binary.
- **A dialog is a raised surface** (`bg-bg-raised`), so a bordered field inside it is `bg-bg`, and so is a card shown inside it. The role and `aria-modal` are on the backdrop element, which is what `usePopoverDismiss`, the shortcut handler and `cardClick.ts` look for.
- **No app-wide shortcut runs while a modal or a confirmation is open** (`shortcutBlocked` and `MODAL_SELECTOR` in `src/lib/escapeKey.ts`). With the zap dialog up and focus on a button, `n` used to switch to the feed behind it and `?` opened Help on top. That includes `?` while Help is open: Escape closes Help. The one exception is Ctrl+Shift+D, the debug panel, which works everywhere on purpose.
- **A popover or menu closes through `usePopoverDismiss`** (`src/hooks/`): Escape, and a click outside that is swallowed. The note menus, the emoji picker, the account menu and the streaming popover in the player bar all use it. The last two were toggle-only and stayed open across navigation. The note menus, the account menu and the streaming popover put focus back on their trigger when Escape closes them; the emoji picker does not yet.
- **What counts as "inside" is the whole control group, not just the popover.** The note action row is inside for its menus. The player bar is inside for the streaming popover (`data-player-bar`): with sats streaming, the first click on pause must not be the one that only closes a popover.
- **The account menu's dismiss is off while the removal confirmation is showing.** There Escape backs out of the confirmation and nothing else, and a stray click must not dismiss a question about deleting a key.
- **Something shown only on hover must also show under keyboard focus.** The relay status list was hover-only: its badge is focusable now, the list is its `role="tooltip"` description and is always in the page (hidden until wanted), and it opens on focus only when the focus came from the keyboard, or a click would pin it open. Row actions that appear on hover (`opacity-0 group-hover:opacity-100`) also take `focus-visible:opacity-100`, or Tab lands on an invisible button.
- **Check a change here in the running app**, with the keyboard: open it from a button, Tab twelve times, press Escape, and see where focus is.

## Buttons

An action with a label is a `Button` (`src/components/shared/Button.tsx`). Before October 2026 every button was the same outlined rectangle, written out by hand about ninety times. Zap, Follow, Mute and Message on a profile were told apart only by the colour of their text, the dim ones read as disabled, and no screen said which action was its main one.

- **Three levels, chosen by how much the action matters on the screen it is on.** `primary` is filled: the one thing this screen or dialog is for (Post, Publish, Follow, Log in). `secondary`, the default, is a quiet fill: everything else worth a button. `ghost` has no box until hovered: Cancel, Back, and actions in a dense bar such as the article reader's header. A screen with two primaries has none.
- **A primary can be `tone="danger"` or `tone="zap"`. A ghost can be `tone="danger"`.** Danger primary is the confirm of something that cannot be undone (Remove account). Zap primary sends sats. A danger ghost is quiet at rest and red under the pointer (Mute, Unfollow).
- **There is no coloured secondary, on purpose.** A status colour is only held at 4.5:1 on a bare surface. Red text on the secondary fill is below that in three themes (3.99:1 in Nord on a raised surface). Give a secondary a coloured icon instead (`<Zap className="text-zap" />Zap`): an icon is a graphic, held to 3:1, and the theme tests check it.
- **The secondary fill is a tint of the text colour** (8%, and 14% under the pointer), so one button works on the canvas, in the sidebar and in a dialog. A fill taken from a surface token disappears on that surface. The two numbers are `SECONDARY_TINT` in `Button.tsx`: the theme tests compute their rules from it, and a Button test holds the class names to it.
- **The hover of a solid fill is its own token** (`accent-hover`, `zap-hover`, `danger-hover`), never the fill at 90%. A translucent fill lets the surface through: on a light theme that lightened the zap button under its light label, to 4.09:1 in Reader. A new theme needs all three, and the tests check the label on each.
- **Hover is written `not-disabled:hover:`.** A disabled button must not react, and `enabled:` would never match a link drawn with `buttonClass`.
- **Sizes are minimum heights: `sm` 28px, `md` 32px, `lg` 40px.** A fixed height left a button 2px short of the field beside it. In a row that stretches its items (a plain `flex`, without `items-center`) the button takes the field's height. `lg` is for the single action of a form or a first-run step, and only a large primary is medium weight.
- **`pressed` makes it a toggle** (Save, Subscribe, Help): `aria-pressed`, and an on state in the accent. **`current` is for "you are here"**: the same look, announced as `aria-current="page"` instead, for a sidebar row or footer button that leads to a view and that pressing again does not switch back. A pressed secondary takes the accent tint. A pressed ghost takes accent text and no fill, which is the one to use on a row that hovers: accent on its own tint is not held at 4.5:1 on the hover surface. `pressed` is for something that can be switched back. An action that happens once (Repost, Like) is `disabled` when done, and a button that opens a region (Comment) says so with `aria-expanded`.
- **`busy` while the action is in flight, `disabled` when it cannot be used.** Same reason as for a switch: a button that disables itself when pressed drops keyboard focus to the page. `busy` keeps focus, ignores clicks, sets `aria-busy` and `aria-disabled`, and shows a spinner in the icon's place. It does not dim the label: "Publishing…" at 60% opacity was 2.8 to 3.8:1. Where one condition used to cover both, write `disabled={cannot && !pending} busy={pending}`.
- **A button whose width must not change while it works keeps its label and has an icon** (Refresh). The spinner is the icon's size, so the two swap in place.
- **`type` defaults to `"button"`.** 210 of the 212 hand-written buttons had none, and a bare `<button>` inside a form submits it. Ask for `type="submit"` when you mean it.
- **`className` is for layout only**: `w-full`, a margin, `self-end`. Never a size, a colour or padding. Two utilities for one property are ordered by the stylesheet, not by the order you wrote them in.
- **A label stays on one line, and the button does not shrink.** So a label that holds text someone else wrote (a name) must be cut: `<span className="max-w-48 truncate">Zap {name}</span>`. One long author name pushed the article reader's other actions off the window. A row of several buttons takes `flex-wrap`. `wrap` lets a label wrap and the button grow, for a full-width button in a narrow column: "Couldn't read the key. Copy it from Settings." does not fit a 192px sidebar.
- **Icons are Lucide components passed as children**: before the label, or after it for an arrow that says where the button leads. The button sizes and thins them. Do not write a glyph (⚡, ✉, →, ✓) into a label.
- **The follow button is `FollowButton`** (`src/components/shared/FollowButton.tsx`). It was written four times with three looks. Not following is a primary "Follow". Following is a quiet "Following" that reads "Unfollow" in red under the pointer or the keyboard focus, but not until the pointer has left once after a press, or following someone would end on a red "Unfollow". It ignores a second press while the first is publishing: the store changes the list at once, so the second press would land on the opposite action. It is absent for a read-only account and on yourself. While the follow list loads it waits, and if the list could not be loaded it is a quiet secondary, because the person may already be followed. The note menu's "Follow" and "Unfollow" items are the one other place that changes the list.
- **Someone unfollowed from the People list keeps their row until the view is left** (`keepUnfollowedRows` in `src/lib/contacts.ts`). A row that vanished on a press put the next person's button under the pointer, and a second press unfollowed them too.
- **Actions in a header run from the quietest on the left to the main one at the right edge** (Mute, Zap, Message, Follow on a profile).
- **A link that has to sit beside a button and read as one takes `buttonClass(...)`.** An external "Open" next to "Connect" is a link, not an action.
- **Not a `Button`**: a chip (a hashtag, a reaction pill, an interest, an amount), a segment of a choice, a row that is tinted when selected, a row that is a card, a round icon control, the dot that removes an attachment. Also not converted yet: the small text actions inside a row or a field (copy, reveal, remove on a list row, "Add" on a suggested relay). They are 18px targets, some shown only on hover, and belong to the rework of those rows.
- **`src/lib/handBuiltButtons.test.ts` is a ratchet over every `<button>` that draws its own box**: the button radius with a fill or an outline, any fill in a token colour, or an outline with padding. A file may lose them and never gain one. It cannot see classes kept in a constant, a box built from another element, or one drawn by a stylesheet.

## Switches

An on/off setting is a `Switch` (`src/components/shared/Switch.tsx`). Before October 2026 the same switch was written out ten times with two knob implementations, each a bare `<button>` with no role and no state, so a screen reader could not say whether a setting was on. Two of the ten had no name either.

- **`Switch` brings its label; `SwitchControl` is the switch alone.** Use `Switch` wherever the label sits beside the control. `SwitchControl` is for a row that lays out its own label (label left, switch right). It does not compile without `aria-labelledby` or `aria-label`, and it takes an `id` so the row's `<label htmlFor>` toggles it. A call site like that gets its own test (`V4VSettings.test.tsx`): the name is a reference between two elements, and nothing else notices when one side is renamed.
- **On and off is said one way.** Not a button whose label is the state: the easy-read font setting was a button reading "Off", which could have been what it is or what pressing it does. Segments are for a choice between named options (font size, relay authentication), where neither option is "off".
- **The label says what turning it on does, and does not change with the state.** What on and off each mean goes in `hint`, which may change. A hint must not open with the state ("Off. Turn on only if..."): it is read out straight after "switch, off".
- **The hint is outside the label, and the label is only as wide as its text.** Clicking the label toggles. A paragraph of explanation must not, and neither must the empty space beside a short label: a full-width label put a strip across the whole Settings pane that restarted every relay connection when clicked. The hint is tied to the switch with `aria-describedby`, and is `text-muted` because it is where the consequence of the setting is explained.
- **`busy` while a change is applied, `disabled` when the setting cannot be used.** A switch that disables itself on Space drops keyboard focus to the page, and the next Space does nothing. `busy` keeps focus, ignores clicks and sets `aria-busy` (relay reach, while connections restart). `disabled` is for "not available": say why in the hint, and say the true reason. "Follow some people first." was shown while the follow list was still loading.
- **The off track is `bg-border-strong`**, the field-edge colour, which the theme tests hold at 3:1 on the canvas and on raised surfaces. It is not held there on a hovered row.
- **`onChange` receives the new state.** A store action that takes no argument is wrapped (`onChange={() => toggle()}`), never passed bare, or it is called with a boolean it does not expect.
- **Focus is drawn with an outline and an offset, not a ring with an offset colour.** The gap of an outline is transparent, so it is right on any surface, and it survives forced-colours mode.

## Type scale

Seven steps, defined as `--text-*` tokens in `src/index.css` and used as `text-micro` to `text-display`. Each sets a size and a line height. Before October 2026 there were 726 hard-coded sizes, 656 of them 12px or smaller, and the note body was 13px.

| Step | Size / line | Used for |
|---|---|---|
| `text-micro` | 11 / 16 | badges, counts, uppercase section labels, `kbd` |
| `text-caption` | 12 / 18 | timestamps, NIP-05, helper text, tags, the smallest buttons |
| `text-ui` | 13 / 20 | nav rows, buttons, tabs, inputs and other form fields, menu items, rows of controls, compact cards |
| `text-body` | 15 / 24 | note text, names, bios, messages, toasts, empty states, setting labels, anything composed (a note, a reply, a message, an article) |
| `text-title` | 17 / 24 | view titles, card titles, dialog titles |
| `text-heading` | 22 / 28 | profile name, onboarding step titles |
| `text-display` | 28 / 34 | article title, onboarding welcome |

- **Nothing is below 11px and no sentence is below 12px.** The page default (`body` in `index.css`) is the body step, so text with no size class is 15px.
- **Pick a step by what the text is, not by how big it should look.** A control takes `text-ui`. A sentence someone reads takes `text-body`, or `text-caption` when it only annotates something. An uppercase label takes `text-micro`. A title takes `text-title` whatever tag it is in, and a sub-heading inside a view takes `text-body font-medium`, so it does not compete with the view's title.
- **Names are `text-body`, even when the name is a button.** The exception is a name inside a compact row that sets its own size: a quote preview, the ancestor chain, an article's byline, the account menu.
- **Where you compose is `text-body`; a field in a form matches the form.** The compose box, replies, messages and the article editor are body size. A bio or a summary sitting among `text-ui` inputs is `text-ui` too.
- **`src/lib/typeScale.test.ts` is a ratchet.** It counts hard-coded sizes (`text-[11px]`, `text-sm`, ...) per file, in `.tsx` and `.ts`. A file may lose them and never gain them. What is left (51) are icon sizes: a lone glyph, an emoji, the initial in an avatar placeholder, the wordmark. Lower the number in the test when you replace one with an icon. It cannot see a size set in a stylesheet or an inline style, or a swap within one file that leaves the count unchanged.
- **Size and line height come from the step. Weight does not.** Use `font-medium` or `font-semibold` beside it. An explicit `leading-*` class still overrides the step's line height.
- **Anything that changes line height globally must set the steps' `--text-*--line-height` tokens.** A line height on `body` no longer reaches stepped text by inheritance. The easy-read font setting does this in `index.css`.
- **A fixed-width box around text has to be checked when a step changes.** The theme picker's `w-20` buttons cut "Hackerman" off at the new size, the Help dialog wrapped a line, and a hint beside "Sign out" was truncated in the sidebar. Prefer `min-w-*` and let the text set the width. An automated overflow scan found none of these; looking at the screens did.
- **A size rewrite by script needs its buckets read before it is applied.** The rewrite classified elements by tag and class. It took three tab bars for avatar initials because their labels are built with `charAt(0)`, and sized a Markdown text area as a control because it is monospaced. A reviewer reading every swap found them.
- **The article reader is the one exception**: its sizes are em on a fluid base set in CSS, so the measure follows the window. See "Long-form reading".
- **The font-size setting scales the whole pane** (`zoom` on `<main>`), so the steps keep their proportions at every setting. Small is close to what Normal was before this scale. The sidebar is outside `<main>` and does not scale.

### The feed's row-height estimate

`src/lib/feedEstimate.ts` tells the virtual list how tall a row will be before it is rendered. When it is far off, each row snaps to its real height on first measurement and the list jumps on upward scroll.

- **It depends on the body step and on each card's layout.** Its constants were measured against rendered rows, not chosen by eye: compare `estimateNoteHeight` with each row's `getBoundingClientRect().height` in the running app. Measured on 2026-10-11: notes 3.3% mean error on Global (31 of 31 within 15%) and 1.4% on Trending (30 of 32), article cards 0.9% (33 of 33). The flat value article cards had before was 18.7% off. If the body step or a card's layout changes, measure again.
- **It counts what a note shows, not what was written.** A link counts as its shortened form, a mention as a name, an article reference as a title, and zero-width padding as nothing. Counting the raw text put one 800-character URL down as fifteen lines.
- **It must never be asked for a width it cannot know.** The feed stays mounted while hidden and reports a width of 0, and the list still asks for estimates then. `Feed.tsx` answers with a flat number in that case. The estimator's cache is per column width and is dropped when the width changes.
- **Each link card has its own height.** A YouTube card (98) is taller than a Spotify one (74) because of its thumbnail; one number for both was 24px off for one of them.

## Theme tokens

Colours are set at runtime by `applyTheme()` from `src/lib/themes.ts`. The `@theme` block in `src/index.css` only supplies the first paint and tells Tailwind which utilities exist, so a colour changed there alone does nothing once the app has started. The October 2026 UI review found the most used text colour (`text-dim`, 431 uses, mostly at 10 to 11px) at 3.0 to 3.7:1 in all eight themes, and the default theme's primary button label at 2.7:1.

- **`src/lib/themes.test.ts` computes the rules from the values**, for every theme, so a new theme or a tweaked colour that breaks one fails there:
  - text, muted, dim and accent reach 4.5:1 on all three surfaces, and the three text levels stay distinct;
  - labels reach 4.5:1 on the fill they sit on and on its hover (`accent-text` on `accent` and `accent-hover`, `zap-text` on `zap` and `zap-hover`, `danger-text` on `danger` and `danger-hover`), and each hover is a visible step from its fill;
  - a secondary button's label reaches 4.5:1 on its fill on all three surfaces, the fill is a step from the surface, and a status-coloured icon on it reaches 3:1;
  - accent reaches 4.5:1 on its own 10% tint (`bg-accent/10 text-accent`: the active tab, nav row and chip);
  - status colours reach 4.5:1 on all three surfaces, hover included, because a zap count or a relay's latency is read on a hovered row;
  - a field's edge reaches 3:1 on the canvas and on raised surfaces;
  - the surfaces stay apart, and the hover surface stays within 1.35:1 of the canvas, because it is the worst case for dim text.
- **`text-dim` is for text people are not required to read.** It now passes AA, but it is still the quietest level. Sentences a new user must read take `text-muted` or `text`. Never stack `opacity-60` on it: ten empty-state sentences did, at 2.4 to 3.1:1.
- **Three border roles, three strengths.** `border-border-subtle` (about 1.45:1) for dividers between rows and regions. `border-border` (about 2:1) for the outline of something you can see the edge of: cards, chips, segments, and the rails that show thread depth. `border-border-strong` (3:1 or more) for edges that say "you can type or switch this": inputs, selects, textareas and the off state of a toggle (`bg-border-strong`). One colour used to do all three at 1.2 to 1.8:1, too strong to recede and too weak to mark a field.
- **A focused field takes `focus:border-accent`, solid.** The old `focus:border-accent/50` was tuned against the faint border. Against `border-strong` it made a focused field's edge *lighter* than a resting one in six of seven themes, with the outline removed.
- **Never write white, or any fixed colour, on a token fill.** Use the fill's label token. `text-white` on `bg-danger` was 2.3 to 3.2:1 in every dark theme, because their danger is light.
- **`hover:bg-bg-hover` is the hover for things on the canvas. On a raised surface use `hover:bg-text/8`.** `bg-hover` is only 1.06 to 1.19:1 from `bg-raised`, so on the sidebar and in menus it shows almost nothing. A tint of the text colour is a step from whatever is under it. Use it on rows whose text is `text-muted` or stronger; dim text does not pass on it.
- **Corner radii, by role.** `rounded-sm` is 6px (`--radius-sm` in `index.css`) for buttons, chips, count badges and reaction pills. `rounded-lg` (8px) for cards, fields, popovers, dialogs, toasts and media, including images and code blocks in articles. `rounded-full` for avatars, status dots and toggles. Full-width rows such as the sidebar's nav rows have none. Do not use `rounded-md`: it is also 6px, a second name for one value. A rounded container whose children are filled to its edge (a segmented control, a toast with a colour stripe, a menu) also needs `overflow-hidden`. Person avatars and their letter placeholders are always round. Podcast and album artwork is not an avatar.
- **The sidebar sits on `bg-raised`**, the feed on `bg`. In the light themes the canvas is the tinted surface and the card is the lighter one, so "raised" still reads as raised.
- **The first-paint colours in `index.css` must equal the default theme.** A test compares them. If they drift, the app flashes the old colours on every launch.
- **Removing a theme needs an entry in `RETIRED_THEMES`.** A stored id that matches nothing applies no theme, and the user is moved to Midnight without a word. `resolveThemeId` follows the map to a theme that exists, and the store writes the replacement back. An id this build does not know at all is shown as the default but left in storage: it may belong to a newer build. Sepia (a dark brown theme, despite the name) was cut this way and maps to Gruvbox.
- **Values were computed, then looked at.** A ratio says a colour is legible, not that it looks right. Check a changed token in the running app, in the theme it belongs to.
- **Known gaps.** Translucent text (`text-accent/60`, `text-accent/80` hashtags) and status text on its own tint (`text-warning` on `bg-warning/10`) are not covered by the tests and fall below 4.5:1 in some themes. Reader's raised surface is 1.03:1 from its canvas. The podcast player bar is still `bg-bg` under the raised sidebar.

## The note action row

`NoteActions.tsx`, rebuilt after the October 2026 UI review. It was seven Unicode glyphs in targets 8 to 22px wide (Repost was 8×22), separated by gaps that all opened the thread, so aiming at Reply and missing by a few pixels changed the view. On the feed, 27 of 49 on-screen targets were under 24px.

- **Which clicks on a card open its thread is decided in `src/lib/cardClick.ts`** (`opensThread`), not in the component, so each exception has a test. Add new exceptions there.
- **From the action row down, nothing is "the card".** `NoteCard` wraps the row and the inline reply box in one `data-no-navigate` area whose negative margins run it out to the card's left, right and bottom edges. A near miss does nothing. It must not snap to the nearest action either: the neighbour may publish. If the card's padding or avatar column changes, change those margins with it.
- **Actions are 16px Lucide icons in 32px buttons, in a fixed order**: Reply, Repost, React, Zap, then reaction pills, with Bookmark and More at the right edge. Anything conditional goes *after* the fixed group (Zap is last of it, pills follow), so no action changes position between notes. Do not insert counts or pills mid-row.
- **Nothing in the row publishes on its first click except a reaction pill.** Repost and Quote share one menu. One-click repost on an 8px target was the reason for the rule.
- **A failed repost or reaction raises a toast.** Both used to end as an unhandled rejection with the menu closed and nothing changed.
- **"Reposted" and "reposting" live in `stores/reposted.ts`, keyed by account and note.** Feed rows are virtualised: a row scrolled away and back is a new component, and local state forgot both, so the note could be reposted twice. Keyed by account because one account's repost must not show as another's after a switch.
- **More is always visible and present on your own notes.** It was hover-only and absent on own notes, which left no way to copy your own note's ID. It offers Follow only once the follow list has loaded (see the contact list section): before that, "not in the list" proves nothing.
- **One popover per row, dismissed through `usePopoverDismiss`** (`src/hooks/`). It adds Esc (via `useEscapeToClose`) and an outside-click listener that *swallows* the click, so closing a menu never also opens the note, link or button under the pointer. The whole row is "inside", so going from one menu straight to another action is one click. The old menus used a `fixed inset-0` backdrop, which a transformed feed row turns into a note-sized rectangle; the shared `EmojiPicker` had the same backdrop and now uses the hook too.
- **That listener is on `window`, capture phase, and must stay there.** `App.tsx` opens external links from a capture listener on `document` that is registered at startup. A later listener on the same node runs after it, and `stopPropagation` does not stop listeners on the same node, so on `document` clicking away onto a link closed the menu and opened the browser.
- **It closes without swallowing in two cases**: its own view is hidden (the feed is hidden, not unmounted, when a shortcut changes view) or a dialog has opened over it. In both the click belongs to something that appeared after the popover did.
- **Popovers open upward when they fit, else downward, else on the roomier side** (`measureRoom` and `pickSide` in `src/lib/popoverPlacement.ts`). The first note under the compose box cut an upward menu off at the top of the scroll area. Room is measured against the nearest `.overflow-y-auto` ancestor, so a list of notes must scroll in an element with that class. The reaction picker wraps to two rows when one row would run past the right edge.
- **Compare rects with rects, never a rect with a pointer position.** Text size is a CSS zoom on `<main>`, and engines disagree on whether `getBoundingClientRect` reports zoomed boxes. `measureRoom` derives the factor from the trigger itself. A rule like "the click was below the action row's top" would mix the two and cannot be checked in WebKitGTK from a Chromium harness, which is why the dead area under the row is built from markup instead.
- **A wrapper that is its own stacking context must lift itself while a popover is open inside it**: `has-[[data-popover-open]]:z-10`, plus `relative` if it is not positioned. Two exist. Feed rows (the virtual list's transform) and read notifications (`opacity-50`, which also needs `opacity-100` or the menu is drawn at half strength). Without it a downward menu is painted under the next item. Plain lists of cards need nothing.
- **Closing a popover from the keyboard or by choosing an item returns focus to its trigger.** Otherwise the focused item unmounts and focus falls to `<body>`. For the same reason the triggers are never `disabled` while a publish is in flight; they are dimmed and marked `aria-busy`. Arrow keys, Home and End move within the open popover, Tab closes it, and it takes focus on open only when opened from the keyboard.
- **Selecting note text is told apart from a click by pointer travel** (`isDrag` in `src/lib/pointer.ts`), never by "is there a selection". A selection outlives the gesture, and clicking `user-select: none` chrome does not reliably clear it, so that test can leave every card ignoring clicks.
- **Clicking the note a thread is already about does nothing.** It used to push a duplicate onto the back stack, so Back appeared to do nothing once.

## Destructive actions and the secret key

- **Removing an account deletes its nsec from the OS keychain** (`removeAccount` → `delete_nsec`). For someone who created the account in Vega and never saved the key, that is the only copy. It is confirmed in `AccountSwitcher.tsx` (`RemoveAccountConfirm`), which offers to copy the key first. Any new path to `removeAccount` must go through a confirmation too. "Sign out" keeps the key and needs none.
- **A failed keychain write must be said out loud.** `store_nsec` is best-effort; when it fails the key lives only in the session and the next launch signs the user out. `debug.warn` is silent in release builds, so `loginWithNsec` raises a toast. On Linux a missing secret service is a normal configuration, not an edge case.
- **Copy about the key must match what the code does.** The backup step said "Vega never stores it" for months while the same function wrote it to the keychain. If key handling changes, change that screen.
- **Esc is decided in `src/lib/escapeKey.ts`, for what is left once nothing is floating.** "Back" only happens when the view stack has something in it. `setView` (sidebar navigation) clears the stack; the `open*` actions push onto it. A dialog, a menu, a tooltip or the editor's zen mode takes Escape first, through `src/lib/layers.ts`, and stops the event, so one press closes one thing and never also navigates. Two things are still closed by the app-wide handler itself: the debug panel, and Help in the moment before its code has loaded. See "Dialogs, popovers and the keyboard".
- **Publishing an article opens the published article**, and only then deletes the draft; success is also said in a toast. A publish no relay accepted never reaches that point: NDK throws `NDKPublishError`, the sheet stays open with the reason, and the draft is kept.

## App identifier & data migration (v0.14.0)

The identifier is **`com.veganostr.Vega`** (was `com.hoornet.vega` before v0.14.0). It must stay on a domain the project controls — **Flathub rejects anything else**, and it keys the app ID for winget and the native installers too.

- **Never migrate app data from inside `.setup()`.** Tauri builds the config-defined windows *before* invoking the setup hook, and building a webview unconditionally `create_dir_all`s `<LocalData>/<identifier>` — which on Linux is the same directory holding `vega.db`, `relay.db` and localStorage. A migration running in `setup()` therefore always sees a non-empty destination. `migrate_legacy_data_dirs()` runs at the **top of `run()`, before `tauri::Builder`**, and uses the `dirs` crate (no `App` needed). Do not move it back.
- **Never use "destination is empty" as the migration trigger** — it is guaranteed non-empty after one launch, so the failure is self-sealing and unrecoverable. Migrate entry-by-entry; never overwrite an entry that already exists at the destination.
- **localStorage is not in the app data dir on every platform.** Linux → data dir (WebKitGTK). Windows → `%LOCALAPPDATA%` (WebView2 `EBWebView/`), *not* `%APPDATA%`. macOS → `~/Library/WebKit/<bundle-id>`. Migrating only `app_data_dir` silently loses themes, drafts, podcast subs and read-state on Windows and macOS.
- Keys are safe across identifier changes: `KEYRING_SERVICE` is the hardcoded literal `"wrystr"`, independent of the identifier.
- **Changing the identifier makes Windows treat the app as new** — it installs alongside the old version rather than upgrading in place. Document it; it's a one-time manual uninstall for users.
- The v0.10.0 Wrystr→Vega rename did this *without* a migration and silently stranded a full data directory (768 MB found on the dev machine). That is what this machinery exists to prevent.

## Hard-won Linux/WebKitGTK lessons

- **Startup/lifecycle changes must be verified by running the real binary**, not unit tests. The v0.14.0 migration had four passing unit tests and would still have wiped every Linux user's data — the defect was in *when* it ran, which no unit test could see. Run it against a scratch env: `XDG_DATA_HOME=/tmp/scratch ./target/debug/vega`, with data seeded beforehand and asserted after. Note `#[cfg(target_os = "...")]` branches are never type-checked on the build host.
- **WebKitGTK does not evict decoded bitmaps** under memory pressure the way Chromium does. Any path that multiplies `<img>` elements per feed page will translate ~linearly into WebProcess RSS. Validate new "render as image" heuristics (e.g. Blossom SHA-256 URLs) with a real content-type probe before shipping.
- **`MemoryPressureSettings` set on `WebsiteDataManager` only affects the NetworkProcess**, not the WebProcess where decoded bitmaps live. Setting a WebProcess cap requires reaching `WebContext` at construction time (construct-only GObject property).
- **The WebKit side of that is long done — don't go looking upstream.** [WebKit bug 222738](https://bugs.webkit.org/show_bug.cgi?id=222738) added `WebKitMemoryPressureSettings` and landed in r280155 on 2021-07-21, and the `webkit2gtk` crate we already depend on exposes it as `WebContextBuilder::memory_pressure_settings()` behind its `v2_34` feature. **The sole remaining gap is wry**, which constructs its own context with `WebContext::new_ephemeral()` and offers no hook to inject settings — verified in wry 0.55.1, which contains no memory-pressure references at all. Getting a WebProcess cap means patching wry, not waiting on WebKit.
- **And we do not currently need one.** The OOM that prompted this was the Blossom `<img>` regex, fixed in v0.12.8. Memory now oscillates ~0.85–1.6 GB, which is an elastic cache passing the test two rules below, not a leak. A cap would be treating a symptom we no longer have.
- **Bisect regression windows before investigating root cause.** If memory behavior changed between versions, `git bisect` the release tags first. Four days of WebKit-level investigation was avoidable once the regression was traced to a single commit in v0.12.6.
- **Distinguish caches from leaks.** Oscillating memory = elastic cache (fine). Monotonic growth = leak or uncapped working set (fix it).
